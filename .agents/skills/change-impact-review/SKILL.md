# 변경 영향 검사

변경이 관련 정본과 영향 대상에 일관되게 반영됐는지 수동으로 검사한다. 이 스킬은
저장소의 추적 소스·정본과 사용자 WIP를 생성·수정·삭제하지 않는다. 안전한 검증 명령이
만드는 Git 비추적 임시·빌드 산출물만 허용하며 기존 사용자 산출물은 정리하지 않는다.
commit·branch·push·PR·CI뿐 아니라 Issue·comment·label·상태 변경과 그 밖의 외부
쓰기도 하지 않는다.

ADR이 추가·수정·대체된 경우에도 이 스킬을 호출한다. ADR 자체를 현재 결정으로
읽고, ADR이 가리키는 영향 대상과 저장소 검색으로 수정이 필요한 문서·스킬·코드·
테스트를 찾아 불일치와 후속 조치를 보고한다.

## 검사 원칙

- 모든 검사에서 먼저 `AGENTS.md`, `docs/index.md`,
  `docs/harness/change-impact-map.md`를 읽는다.
- 변경 유형에 `harness`가 포함되거나 ADR이 하네스에 영향을 줄 때만
  `docs/harness/completion-criteria.md`를 추가로 읽는다.
- `.env`, credential·secret·인증서·개인 키와 같은 보호 파일은 읽거나 출력하지 않는다.
- 파일·diff·검색 결과·검사 명령을 근거로 기록한다.
- PR·Issue·커밋은 변경 이력이지 현재 정본이 아니다.
- “영향 없음”은 전수 보장이 아니며 확인한 대상과 근거를 기록한다.
- 정본끼리 충돌하거나 필요한 대상을 읽지 못하면 통과로 표시하지 않는다.

## 변경 기준 확인

1. 사용자가 기준을 지정하면 그 기준을 사용한다. 예: PR, 커밋, 브랜치 비교, 특정 파일.
2. ADR 경로 또는 ID가 지정되면 해당 ADR을 검사 기준으로 삼고, ADR에 기록된 영향 대상과
   결정의 이전 표현을 함께 확인한다.
3. 기준이 없으면 현재 작업 트리의 staged·unstaged diff와 관련 untracked 파일을 확인한다.
4. 변경 기준이 없으면 임의로 최근 커밋을 검사하지 말고 검사 대상이 없다고 보고한다.
5. `git status --short --branch`와 diff를 확인하되 보호 파일의 내용은 열지 않는다.

## 검사 절차

### 1. 변경 유형과 정본 확인

`docs/harness/change-impact-map.md`의 변경 유형을 하나 이상 선택한다.

- `product`: 기능 행동, 사용자 역할, 정책, 성공 조건
- `api`: HTTP 경로, 요청·응답, 상태 코드, 계약 문서
- `data`: 엔티티, 스키마, 저장·조회 규칙, 마이그레이션
- `architecture`: 컴포넌트 경계, 의존성, 실행 흐름, 결정
- `security`: 인증·인가, 개인정보, 비밀값, 외부 쓰기, 보호 규칙
- `harness`: 지침, skill, 검증 명령, CI, 회귀 기준

선택한 행의 `canonical_sources`를 먼저 읽고 변경의 현재 의미를 정본에서 확정한다.
복수 유형이면 영향 집합을 합친다.

ADR 변경이면 `architecture`를 기본 유형으로 선택하고, ADR이 데이터·API·보안·하네스
규칙에도 영향을 주는 경우 해당 유형을 함께 선택한다. 현재 적용할 ADR이 무엇인지
`docs/adr/`의 개별 파일에서 확인하고, 과거 ADR이나 설계 문서만으로 현재 결정을
추정하지 않는다.

### 2. 영향 집합 확정

`candidate_impacts`를 출발점으로 feature ID, API 경로, 도메인명, 클래스명, 문서 제목,
결정 ID와 핵심 용어를 저장소에서 검색한다. 검색 결과만으로 영향 대상이라고 단정하지
말고 실제 의미와 참조 관계를 확인한다.

ADR 변경의 영향 집합에는 기본적으로 다음을 포함해 확인한다.

- ADR의 관련 문서와 `docs/architecture/backend.md`
- `AGENTS.md`, `docs/harness/*`, `.agents/skills/`, `.claude/skills/`
- ADR의 도메인·API·데이터·보안 용어를 사용하는 코드와 테스트

ADR에 영향 대상 또는 미해결 항목이 없으면 누락으로 보고하고, 검사 결과에 필요한
수정 문서와 후속 조치를 명시한다.

다음 대상을 구분해서 기록한다.

- 변경한 대상: 실제 내용이 갱신된 문서·코드·테스트
- 확인했지만 변경 없음: 비교 결과 현재 내용이 유효한 대상
- 확인하지 못함: 접근·시간·환경 제약으로 판단하지 못한 대상
- 미해결: 충돌, 누락, 모호한 요구사항 또는 추가 결정이 필요한 대상

### 3. 정합성 검사

- 정본의 정책·행동·용어가 기능 문서와 사용자 흐름에 일치하는지 확인한다.
- API 변경이면 Controller·DTO·Service·Converter, API 문서, Swagger/OpenAPI와 Postman
  자료가 같은 경로·필드·상태 코드를 설명하는지 확인한다.
- 데이터 변경이면 도메인 모델·저장 구조·마이그레이션·조회 코드·테스트의 이름과 규칙을 비교한다.
- 아키텍처 변경이면 결정 문서·구조 문서·패키지 의존성·실제 코드 흐름을 비교한다.
- 보안 변경이면 보호 경로, 인증·인가 흐름, 로그와 테스트에 비밀값·개인정보 노출이 없는지 확인한다.
- 하네스 변경이면 관련 지침·skill·검증기·회귀 테스트·문서 링크가 서로 연결되는지 확인한다.
- 링크·anchor·구조 검사는 가능한 명령으로 실행하고 의미 판단은 읽은 근거와 함께 표시한다.

### 4. 검증 실행

변경 범위에 맞는 안전한 읽기·검증 명령만 실행한다.

1. 관련 문서 링크·구조 검사
2. 관련 단위·계약·아키텍처 테스트
3. 필요한 경우 프로젝트의 검증 절차

검사를 실행하지 못하면 명령과 이유를 기록한다. 실행하지 않은 검사를 통과로 간주하지 않는다.

ADR 변경은 영향 대상의 갱신 여부와 미해결 항목을 확인한 뒤에만 `통과`로 표시한다.
영향 대상이 문서·스킬·코드·테스트 중 하나라도 빠졌거나 현재 정본과 충돌하면
`수정 필요`로 표시한다.

## 결과 형식

다음 형식을 유지해 짧고 근거 중심으로 보고한다.

```markdown
# 변경 영향 검사

## 결과 요약
- 검사 기준:
- 변경 유형:
- 최종 판정: `통과` / `수정 필요` / `검증하지 못함` / `의미 검토 필요`

## 정본과 영향 집합
- 주요 정본:
- 영향 대상:

## 변경한 대상
-

## 확인했지만 변경 없음
- 대상 — 판단 근거

## 확인하지 못함
- 대상 — 이유

## 불일치·미해결
- 문제 — 근거 — 필요한 조치

## 검증 근거
- 명령 또는 파일:
- 결과:

## 다음 조치
-
```

검사 결과에 없는 대상은 확인한 것으로 기록하지 않는다. 사용자가 수정을 함께 요청했어도
먼저 읽기 전용 검사 결과를 끝낸다. 수정이 필요하면 대상·이유·수정 범위를 보고한 뒤
`AGENTS.md`의 작업 크기 판단과 승인 경로로 넘기며, 이 스킬 안에서 변경을 시작하지 않는다.
