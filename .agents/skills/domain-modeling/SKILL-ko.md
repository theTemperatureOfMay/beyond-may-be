# 도메인 모델링

설계하는 동안 프로젝트의 도메인 모델을 능동적으로 구축하고 정교화한다. 이것은 용어에 이의를 제기하고, 경계 사례 시나리오를 만들고, 용어집과 결정을 명확해지는 즉시 기록하는 **능동적인 규율**이다. `CONTEXT.md`를 어휘 확인을 위해 단순히 읽는 것은 이 스킬에 해당하지 않는다. 모든 스킬이 할 수 있는 한 줄짜리 습관일 뿐이다. 이 스킬은 모델을 변경할 때 사용한다.

## 파일 구조

대부분의 저장소는 단일 컨텍스트를 사용한다.

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

루트에 `CONTEXT-MAP.md`가 있으면 저장소는 여러 컨텍스트를 사용한다. 이 맵은 각 컨텍스트가 있는 위치를 가리킨다.

```
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                          # 시스템 전역 결정
└── src/
    ├── ordering/
    │   ├── CONTEXT.md
    │   └── docs/adr/                 # 컨텍스트별 결정
    └── billing/
        ├── CONTEXT.md
        └── docs/adr/
```

파일은 필요할 때만 지연 생성한다. 기록할 내용이 있을 때만 파일을 만든다. `CONTEXT.md`가 없으면 첫 번째 용어가 확정될 때 만든다. `docs/adr/`가 없으면 첫 번째 ADR이 필요해질 때 만든다.

## 세션 중 절차

### 용어집과 대조하기

사용자가 `CONTEXT.md`의 기존 언어와 충돌하는 용어를 사용하면 즉시 지적한다. "용어집에서는 'cancellation'을 X로 정의했는데, 지금은 Y를 뜻하는 것 같습니다. 어느 쪽입니까?"라고 묻는다.

### 모호한 표현 정교화하기

사용자가 모호하거나 여러 의미로 쓰이는 용어를 사용하면 정확한 표준 용어를 제안한다. "'account'라고 하셨는데 Customer를 뜻합니까, User를 뜻합니까? 둘은 서로 다른 개념입니다."라고 묻는다.

### 구체적인 시나리오 논의하기

도메인 관계를 논의할 때는 구체적인 시나리오로 압박 검증한다. 경계 사례를 탐색하고 개념 간 경계를 명확히 하도록 시나리오를 만든다.

### 코드와 상호 참조하기

사용자가 시스템 동작을 설명하면 코드가 그 설명과 일치하는지 확인한다. 모순을 찾으면 드러낸다. "코드는 전체 Order를 취소하지만, 방금 부분 취소가 가능하다고 했습니다. 어느 쪽이 맞습니까?"라고 묻는다.

### `CONTEXT.md`를 즉시 갱신하기

용어가 확정되면 그 자리에서 `CONTEXT.md`를 갱신한다. 한꺼번에 모아 두지 말고 확정되는 대로 기록한다. [CONTEXT-FORMAT-ko.md](./CONTEXT-FORMAT-ko.md)의 형식을 사용한다.

`CONTEXT.md`에는 구현 세부사항이 전혀 없어야 한다. `CONTEXT.md`를 사양서, 작업 메모 또는 구현 결정을 보관하는 곳으로 취급하지 않는다. 이 파일은 용어집일 뿐이다.

### ADR은 신중하게 제안하기

다음 세 조건이 모두 참일 때만 ADR 작성을 제안한다.

1. **되돌리기 어렵다** — 나중에 생각을 바꾸는 비용이 의미 있게 크다.
2. **맥락이 없으면 의외다** — 미래의 독자가 "왜 이렇게 했지?"라고 생각할 것이다.
3. **실제 절충의 결과다** — 진짜 대안들이 있었고, 특정 이유로 하나를 선택했다.

세 조건 중 하나라도 빠지면 ADR을 건너뛴다. [ADR-FORMAT-ko.md](./ADR-FORMAT-ko.md)의 형식을 사용한다.
