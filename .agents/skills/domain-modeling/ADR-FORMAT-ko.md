# ADR 형식

ADR은 `docs/adr/`에 저장하며 순차 번호를 사용한다. 파일 이름은 `0001-slug.md`, `0002-slug.md`와 같은 형식이다.

ADR이 처음 필요해질 때까지 `docs/adr/` 디렉터리를 만들지 않는다.

## 템플릿

```md
# {결정의 짧은 제목}

{맥락, 결정한 내용과 이유를 1~3문장으로 작성한다.}
```

이것이 전부다. ADR은 한 문단이어도 된다. 가치는 섹션을 채우는 데 있지 않고, 결정이 이루어졌다는 사실과 그 이유를 기록하는 데 있다.

## 선택적 섹션

실질적인 가치가 있을 때만 다음 섹션을 추가한다. 대부분의 ADR에는 필요하지 않다.

- **Status** frontmatter (`proposed | accepted | deprecated | superseded by ADR-NNNN`) — 결정을 다시 검토할 때 유용하다.
- **Considered Options** — 거부한 대안을 기억할 가치가 있을 때만 추가한다.
- **Consequences** — 명확하지 않은 후속 영향까지 짚어야 할 때만 추가한다.

## 번호 매기기

`docs/adr/`에서 기존 번호 중 가장 큰 값을 찾고 그다음 번호를 사용한다.

## ADR을 제안할 때

다음 세 조건이 모두 참이어야 한다.

1. **되돌리기 어렵다** — 나중에 생각을 바꾸는 비용이 의미 있게 크다.
2. **맥락이 없으면 의외다** — 미래의 독자가 코드를 보고 "대체 왜 이렇게 했지?"라고 생각할 것이다.
3. **실제 절충의 결과다** — 실제 대안들을 검토했고, 구체적인 이유로 하나를 선택했다.

결정을 쉽게 되돌릴 수 있다면 건너뛴다. 곧 되돌릴 수 있기 때문이다. 의외가 아니라면 아무도 이유를 궁금해하지 않는다. 실제 대안이 없었다면 "당연한 일을 했다"는 내용 외에 기록할 것도 없다.

### 기록할 만한 결정

- **아키텍처 형태.** "모노레포를 사용한다." "쓰기 모델은 이벤트 소싱을 사용하고 읽기 모델은 Postgres에 프로젝션한다."
- **컨텍스트 간 통합 패턴.** "Ordering과 Billing은 동기 HTTP가 아니라 도메인 이벤트로 통신한다."
- **전환 비용이 큰 기술 선택.** 데이터베이스, 메시지 버스, 인증 공급자, 배포 대상 등이 해당한다. 모든 라이브러리가 아니라 교체에 한 분기 정도 걸릴 선택만 기록한다.
- **경계와 범위 결정.** "Customer 데이터는 Customer 컨텍스트가 소유하며, 다른 컨텍스트는 ID로만 참조한다." 명시적인 금지 사항도 허용 사항만큼 중요하다.
- **당연한 경로에서 의도적으로 벗어난 결정.** "X라는 이유로 ORM 대신 수동 SQL을 사용한다." 합리적인 독자가 반대로 생각할 만한 선택을 기록한다. 그래야 다음 엔지니어가 의도적인 결정을 고치려 하지 않는다.
- **코드에서 보이지 않는 제약.** "규정 준수 요구사항 때문에 AWS를 사용할 수 없다." "파트너 API 계약 때문에 응답 시간은 200ms 이하여야 한다."
- **거부한 대안.** 거부 이유가 쉽게 드러나지 않을 때만 기록한다. GraphQL을 검토했지만 미묘한 이유로 REST를 선택했다면 기록한다. 그렇지 않으면 6개월 뒤 누군가 GraphQL을 다시 제안할 것이다.
