# ClueDoc

저장소를 코드 디렉터리가 아닌 **기능 계층**으로 설명하는 문서를 `.dev/cluedoc/`에 유지한다.
각 기능 문서는 쉬운 개념 설명과 실제 코드로 이동할 수 있는 구현 지도를 함께 제공한다.

`.dev/cluedoc/`은 현재 코드에서 파생한 설명 자료이며 프로젝트 정본이 아니다. 작성 전에
`docs/index.md`와 해당 기능의 정본 문서를 읽는다. 코드와 정본이 충돌하면 어느 한쪽을
임의로 맞추지 말고 불일치와 영향 대상을 사용자에게 보고한다.

## 실행 경계

- 문서 쓰기는 사용자가 초기화·동기화를 요청했거나 승인된 구현 범위에 ClueDoc 갱신이 포함된
  경우에만 수행한다.
- ClueDoc이 쓰는 경로는 `.dev/cluedoc/**`뿐이다. `AGENTS.md`, 정본 문서, 소스 코드, 워크플로,
  훅과 설정을 자동으로 수정하지 않는다.
- 외부 서비스, 비밀값, 백그라운드 프로세스와 별도 인덱스는 사용하지 않는다.

## 기능 계층

기능 하나를 폴더 하나와 그 안의 `README.md` 하나로 표현한다. 저장소 전체 문서는
`.dev/cluedoc/README.md`, 하위 기능은 `.dev/cluedoc/<feature>/README.md`에 둔다. 서로 독립적으로
설명할 가치가 있는 하위 역량만 더 깊게 나누고 코드 패키지 구조를 그대로 복제하지 않는다.

변경된 코드를 문서화할 때 다음 양방향을 함께 추적한다.

1. 호출자와 사용처를 찾아 이 코드가 속한 상위 기능을 확인한다.
2. 피호출자와 의존성을 찾아 기능을 실제로 수행하는 하위 구성요소를 확인한다.
3. 기존 문서의 `sources`를 검색해 영향을 받는 기능 문서를 찾는다.
4. 실제 기능 경계가 달라진 문서만 만들거나 갱신하고, 모든 상호 링크를 다시 확인한다.

## 초기화

사용자가 `cluedoc init` 또는 같은 의미의 초기화를 명시적으로 요청했을 때만 수행한다.

1. `.dev/cluedoc/`에 문서가 이미 있으면 덮어쓰지 않고 일반 동기화를 제안한다.
2. 저장소의 주요 기능 3~7개를 식별한다.
3. 루트 문서와 최상위 기능 문서만 작성하고 더 깊게 재귀하지 않는다.
4. `AGENTS.md`나 다른 에이전트 지침 파일에는 트리거 블록을 삽입하지 않는다.

## 문서 형식

각 문서는 다음 frontmatter로 시작한다.

```yaml
---
title: 기능 이름
sources:
  - src/main/example/FeatureController.java
---
```

`sources`에는 기능과 구현 지도에 등장하는 모든 저장소 상대 경로를 넣는다. 여러 기능이 같은
파일을 공유할 수 있다. 심볼과 줄 번호는 frontmatter에 넣지 않는다.

본문은 다음 여섯 부분을 순서대로 유지한다.

1. 문서 첫머리의 핵심 Mermaid 또는 텍스트 시각화
2. `## Abstract`
3. `## Introduction`
4. `## Related Work`
5. `## Description`
6. `## Conclusion`

`Related Work`에는 이미 존재하는 ClueDoc 문서만 상대 링크로 연결한다. 구조·흐름·상태나
관계는 이해에 실질적으로 도움이 될 때 가장 작은 Mermaid 또는 텍스트 시각화로 보여 준다.

### 구현 지도

모든 문서의 `## Description` 안에 `### 구현 지도 (Implementation Map)`를 둔다. 런타임
흐름이 있는 기능은 다음 열을 가진 표를 실행 순서대로 작성한다.

| 단계 | 동작 | 구현 위치 | 심볼 | 주요 분기·부수 효과 | 다음 호출 |
| --- | --- | --- | --- | --- | --- |

- `구현 위치`는 해당 문서에서 실제 소스 파일로 이동하는 작동하는 상대 Markdown 링크다.
- `심볼`에는 실제 클래스, 메서드 또는 함수 이름을 적는다.
- Controller, 인증·검증, Service·트랜잭션, 저장소·DB, 외부 API, 폴백, 응답 이후 비동기
  작업 중 해당 기능에 존재하는 경계만 포함한다.
- 호출자와 피호출자를 검색해 경로와 심볼을 확인한다. 추측한 이름이나 존재하지 않는 링크를
  쓰지 않는다.
- 줄 번호는 코드 변경에 쉽게 낡으므로 기록하지 않는다.
- 구현 지도 밖의 본문은 코드 심볼과 경로를 나열하지 않고 도메인 언어로 설명한다.

## 동기화 규칙

- 새 기능은 문서를 만들고 부모 문서의 `Related Work`에 연결한다.
- 기능 경계가 바뀌면 필요한 문서만 분리·이동하고 들어오는 링크를 함께 갱신한다.
- 기능 삭제가 승인된 코드 변경으로 확인된 경우에만 대응 문서를 제거한다.
- 설명만 바뀌지 않은 포맷·이름 정리는 불필요한 문서 재작성을 만들지 않는다.

## 시스템 질문

사용자가 시스템 동작을 질문하고 `.dev/cluedoc/` 문서가 존재하면 먼저 질문에 직접 답한다. 그 뒤
가장 관련 있는 기존 문서 2~5개를 읽는 순서와 이유를 포함한 짧은 `Reading Guide`로 연결한다.
문서가 없거나 링크가 확인되지 않으면 경로를 만들어내지 않는다. 이 과정은 읽기 전용이다.

## 검증

1. `sources`의 모든 경로와 구현 지도의 모든 심볼이 실제로 존재하는지 확인한다.
2. 구현 위치와 `Related Work`의 모든 상대 링크가 현재 문서 위치에서 열리는지 확인한다.
3. 구현 지도에 등장하는 파일이 모두 `sources`에 포함됐는지 확인한다.
4. 진입점부터 마지막 부수 효과까지 단계 순서가 실제 호출 흐름과 일치하는지 다시 읽는다.
5. 변경 diff가 승인된 `.dev/cluedoc/**` 범위를 벗어나지 않았는지 확인하고, 정본과의 미해결
   불일치를 완료 보고에 남긴다.
