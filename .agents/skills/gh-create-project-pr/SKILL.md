# 프로젝트 PR 생성

호출 승인은 저장소·브랜치·템플릿 읽기와 제목·본문 초안 작성까지만 허용한다.
PR 생성은 아래 외부 쓰기 직전 확인에서 최종 대상을 보여 주고 받는 별도 승인이
필요하며, 호출 승인을 생성 승인으로 재사용하지 않는다.

현재 저장소의 규칙과 실제 검증 결과를 기준으로 Pull Request를 게시하라. 제목이나 본문을
대화 기억으로 재구성하지 말고 매번 저장소에서 다시 확인하라.

## 1. 게시 범위 확인

1. 루트 `AGENTS.md`와 현재 경로에 적용되는 중첩 규칙을 읽어라.
2. `.github/PULL_REQUEST_TEMPLATE.md` 전체를 읽어라.
3. 현재 저장소, branch, remote, base branch와 staged·unstaged 상태를 확인하라.
4. 사용자가 요청한 변경만 PR에 포함됐는지 diff와 commit을 확인하라.
5. 열린 PR 중 같은 head branch를 사용하는 PR이 있는지 확인하라.
6. 커밋 또는 PR 요청 시 하네스 갱신 필요성을 먼저 점검하라. 필요한 변경이 있으면
   설명하고 승인받기 전에는 수정하거나 게시하지 마라.

작업 트리에 PR 범위 밖의 변경이 있으면 자동으로 stage하거나 커밋하지 말고 사용자에게
범위를 확인하라.

## 2. 제목 작성

제목은 반드시 다음 형식을 사용하라.

```text
[TAG] 한글 내용
```

- `TAG`는 대문자로 작성하고 대괄호로 감싸라.
- `]` 뒤에는 공백을 정확히 하나 둬라.
- 내용은 변경 전체를 설명하는 간결한 한국어로 작성하라.
- `tag : 내용`, `[tag] 내용`, 영어 본문 형식을 사용하지 마라.
- 제목이 `^\[[A-Z][A-Z0-9_-]*\] .+` 형식인지 게시 전에 다시 확인하라.

변경의 주된 목적에 따라 다음 tag를 선택하라.

| TAG | 기준 |
|---|---|
| `FEAT` | 사용자 또는 개발자 기능 추가 |
| `FIX` | 결함 수정 |
| `REFACTOR` | 동작을 유지하는 구조 개선 |
| `TEST` | 테스트 중심 변경 |
| `DOCS` | 문서만 변경 |
| `CHORE` | 빌드, CI, 하네스, 설정, 도구와 유지보수 |

여러 유형이 섞이면 PR의 가장 중요한 목적 하나를 선택하라. 확신할 수 없고 선택에 따라
리뷰 의미가 달라지면 사용자에게 tag 하나만 질문하라.

## 3. 본문 작성

`.github/PULL_REQUEST_TEMPLATE.md`의 제목, 이모지와 순서를 그대로 유지하라. 현재
템플릿에 있는 다음 섹션을 하나도 생략하지 마라.

```text
## 🚀 변경 사항
## 🔍 주요 변경 내용
## 🔗 관련 이슈
## 🧪 테스트
## 📸 스크린샷
## ✅ 체크리스트
## 💬 리뷰어 참고 사항
```

- HTML 안내 주석은 최종 본문에서 제거하라.
- 관련 이슈가 없으면 `관련 이슈 없음`이라고 명시하라.
- 스크린샷이 필요 없는 변경이면 `화면 변경 없음`과 이유를 적어라.
- 실제 실행한 검사와 확인된 결과만 테스트 섹션에 기록하라.
- 근거가 있는 체크리스트만 `[x]`로 표시하라.
- API 변경이 없으면 Swagger와 Postman이 갱신 대상이 아닌 이유를 적어라.
- 미실행 검사, 실패, 환경 문제와 의도적인 제외 항목을 숨기지 마라.
- 리뷰어가 알아야 할 설계 선택, 제한, 위험과 후속 작업을 마지막 섹션에 적어라.

## 4. 외부 쓰기 직전 확인

PR 생성은 외부 쓰기다. 실행 직전에 다음 최종 내용을 사용자에게 보여 주고 명시적인
승인을 받아라.

- repository
- base와 head branch
- Draft 여부
- 최종 제목
- 최종 본문

사용자가 해당 최종 내용을 이미 명시적으로 승인한 경우에만 같은 내용을 다시 묻지 않고
진행할 수 있다.

## 5. Draft PR 생성

1. branch가 remote에 push됐는지 확인하라.
2. 사용자가 Ready PR을 명시하지 않았다면 Draft로 생성하라.
3. 연결된 GitHub 앱을 우선 사용하라.
4. 생성 결과에서 PR 번호, URL, title, base, head, Draft 상태를 다시 확인하라.
5. 앱이 `403 Resource not accessible by integration`을 반환하면 성공했다고 말하지 마라.
   대상 account·organization·repository 설치와 PR 쓰기 action 권한을 구분해 보고하라.
6. 중복 PR이 발견되면 새 PR을 만들지 말고 기존 PR을 업데이트할지 질문하라.

## 6. CI와 artifact 확인

PR 생성 후 head commit의 workflow를 확인하라.

1. CI가 생성될 때까지 짧은 간격으로 상태를 확인하라.
2. semantic 검증, build와 각 후속 step의 결과를 구분하라.
3. CI가 실패하면 실패한 job과 step을 보고하고, 수정 요청 없이 코드를 고치지 마라.
4. workflow가 JaCoCo 업로드를 포함하면 `jacoco-report` artifact의 존재, 만료 여부와
   보관 기한을 확인하라.
5. behavioral 검증처럼 CI에서 제외하기로 한 검사를 임의로 실행하지 마라.

완료 보고에는 PR 링크, Draft 상태, CI 결론, artifact 결과와 남은 문제를 포함하라.
