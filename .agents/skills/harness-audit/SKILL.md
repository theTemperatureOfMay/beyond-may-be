# 프로젝트 하네스 평가

## 1. 평가 원칙

- 저장소의 `docs/harness/completion-criteria.md`를 유일한 판정 기준으로 사용하라.
- 기준 내용을 이 스킬에 다시 정의하거나 임의로 바꾸지 마라.
- 기본 평가를 읽기 전용으로 수행하라. 파일 수정, 설정 변경, 의존성 설치, 커밋, 외부 쓰기 작업을 하지 마라.
- 사용자의 기존 변경사항을 보존하고 평가 대상과 관계없는 변경을 문제로 취급하지 마라.
- 추측으로 점수를 주지 말고 파일, 설정, 명령 결과처럼 확인 가능한 근거를 사용하라.
- 문서가 존재한다는 사실과 규칙이 실제로 적용된다는 사실을 구분하라.
- 현재 환경에서 확인할 수 없는 항목은 `미확인`으로 표시하고 통과로 간주하지 마라.

## 2. 평가 범위 결정

1. 사용자가 저장소를 지정하면 그 저장소를 평가하라.
2. 지정하지 않으면 현재 작업 중인 저장소를 평가하라.
3. 저장소 루트와 현재 작업 디렉터리를 확인하라.
4. 먼저 저장소의 `AGENTS.md`를 끝까지 읽고 적용하라.
5. `CLAUDE.md`와 하위 지침 파일이 있으면 적용 범위와 우선순위를 확인하라.
6. `docs/harness/completion-criteria.md`를 끝까지 읽으라.
7. 완성 기준 문서가 없으면 점수를 만들지 말고 `평가 기준 부재`로 판정하라.

사용자가 범위를 정하지 않았다면 문서와 설정을 조사하는 정적 평가를 수행하라.
실제 도구 로딩 시험, 테스트, 빌드 또는 회귀 시나리오 실행을 요청했다면 안전한 범위에서 실행 평가를 추가하라.

## 3. 평가 전 상태 확인

- Git 저장소라면 읽기 전용으로 변경 상태를 확인하라.
- 비밀정보 파일은 내용 대신 존재 여부, ignore 여부, 접근 제한만 확인하라.
- `.env`, 키, 토큰, 인증 파일의 내용을 출력하지 마라.
- 평가에 사용할 명령이 소스나 외부 시스템을 변경할 가능성이 있으면 실행하지 말고 필요한 승인과 위험을 보고하라.
- 실제 삭제, 운영 변경, 외부 메시지 전송으로 안전 관문을 시험하지 마라. 설정 검사나 격리된 무해한 시험으로 대체하라.

## 4. 근거 수집

완성 기준의 G1부터 G6까지 순서대로 조사하라.

### G1 공통 지침

- 루트와 하위 `AGENTS.md`, `AGENTS.override.md`를 확인하라.
- `CLAUDE.md`가 공통 원본을 가져오는지 확인하라.
- `.agents/skills/`와 `.claude/skills/`의 원본·연결 구조를 확인하라.
- 전역 규칙은 현재 환경에서 읽을 수 있는 범위에서만 확인하라.
- 파일 구조상 로딩 가능함과 새 세션에서 실제 로딩을 확인함을 구분하라.

### G2 프로젝트 지식

- `README.md`와 `docs/`의 프로젝트 문서를 찾으라.
- 하네스가 일반 프로젝트 문서를 복사하지 않고 올바르게 연결하는지 확인하라.
- 프로젝트 설명을 코드와 빌드 설정의 대표 증거와 대조하라.
- 빈 문서, 끊어진 링크, 코드와 충돌하는 설명을 기록하라.

### G3 안전과 승인

- 지침에 적힌 보호 규칙과 실제 기술적 보호 장치를 따로 평가하라.
- Codex 설정, Claude Code 설정, 권한 규칙, 샌드박스, 훅, CI, ignore 규칙을 확인하라.
- 비밀정보, 삭제, 저장소 밖 쓰기, 배포, 외부 쓰기 작업의 승인 경계를 확인하라.
- 자연어 규칙만 있고 강제 장치가 없으면 이를 분명한 미충족 항목으로 기록하라.
- 안전 실패가 확인되면 점수와 별도로 전체 판정을 실패로 표시하라.

### G4 위험도 기반 작업 절차

- 낮음, 보통, 높음 위험 작업의 절차가 구분되어 있는지 확인하라.
- 작은 작업에 과도한 계획을 강제하거나 높은 위험 작업에 승인이 빠지는지 확인하라.
- 작업 범위 확대, 불명확한 요구, 구현 중 계획 변경의 처리 규칙을 확인하라.

### G5 검증과 완료

- 설치, 실행, 관련 테스트, 전체 테스트, 코드 품질 검사, 빌드 명령을 찾으라.
- 문서의 명령이 실제 빌드 파일이나 스크립트에 존재하는지 확인하라.
- 실행 평가에서는 가장 좁고 안전한 검사부터 실행하라.
- 기존 실패와 이번 평가에서 새로 발생한 실패를 구분하라.
- 실행하지 못한 검사는 이유와 함께 `미확인`으로 남겨라.
- 완료 보고에 변경 내용, 검사, 결과, 남은 위험을 구분하는 규칙이 있는지 확인하라.

### G6 운영과 유지관리

- 하네스 담당자, 변경 절차, 재평가 조건이 있는지 확인하라.
- 반복 실수를 프롬프트, 프로젝트 규칙, 스킬, 훅, 권한 중 알맞은 위치에 반영하도록 되어 있는지 확인하라.
- 실제 평가 결과를 저장하고 비교하는 위치나 절차가 있는지 확인하라.

## 5. 판정과 채점

완성 기준 문서에 정의된 필수 관문과 100점 배점을 그대로 사용하라.

각 관문 상태를 다음 중 하나로 표시하라.

- `통과`: 모든 필수 조건에 확인 가능한 근거가 있다.
- `조건부 통과`: 핵심 조건은 충족하지만 일부 보완이나 실행 확인이 필요하다.
- `실패`: 필수 조건이 충족되지 않았다.
- `미확인`: 현재 환경이나 평가 범위에서 확인하지 못했다.
- `안전 실패`: 즉시 실패 조건을 위반했다.

채점할 때 다음 규칙을 지켜라.

- 근거가 확인된 점수만 부여하라.
- 미확인 항목에 점수를 주지 마라.
- 조건부 통과 항목은 충족된 세부 항목의 점수만 부여하라.
- 점수와 필수 관문 판정을 분리하라.
- 85점 이상이어도 필수 관문 실패나 안전 실패가 있으면 `팀 적용 완성`으로 판정하지 마라.
- 정적 평가만 수행했다면 실제 도구 로딩과 회귀 시험을 완료한 것처럼 판정하지 마라.

## 6. 회귀 시험 처리

완성 기준의 회귀 시험표를 그대로 사용하라.

- 파일과 설정 조사만으로 확인한 결과는 `정적 확인`이라고 표시하라.
- 실제 Claude Code 또는 Codex 새 세션이 필요한 시험은 실행하지 못했다면 `미평가`로 남겨라.
- 현재 도구가 다른 도구의 실제 행동을 대신했다고 주장하지 마라.
- 위험 시나리오는 실제 피해를 일으키지 않는 모의 요청이나 설정 검사로 평가하라.
- 실패한 시험은 근거, 예상 행동, 실제 행동, 필요한 개선을 함께 기록하라.

## 8. 결과 저장

- 기본적으로 평가 결과를 채팅으로만 보고하라.
- 사용자가 저장을 요청한 경우에만 저장소에 평가 문서를 작성하라.
- 저장 위치를 별도로 지정하지 않았다면 `docs/harness/evaluations/YYYY-MM-DD-harness-audit.md`를 제안하라.
- 저장 전에 기존 평가 파일과 사용자의 변경사항을 확인하라.
- 평가 결과 문서에 비밀정보, 토큰, 개인정보 또는 환경 변수 값을 기록하지 마라.

## 9. 평가 후 변경

- 평가 요청만 받았다면 문제를 고치지 마라.
- 사용자가 개선까지 요청하면 평가를 먼저 완료하고 변경 범위와 우선순위를 제시하라.
- 프로젝트의 작업 크기 판단과 승인 절차에 따라 별도 승인을 받은 뒤 수정하라.
- 수정 후 영향받은 관문과 회귀 시험만 우선 재평가하고, 안전 또는 공통 지침이 바뀌었다면 전체 평가를 다시 수행하라.
