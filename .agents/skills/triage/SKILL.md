# Triage

Assess one local Markdown implementation ticket. Recommend what should happen next, but do not
approve implementation or start the next work route.

Every comment drafted during triage must start with this disclaimer:

```markdown
> *This was generated by AI during triage.*
```

## Required references

Read these before assessing a ticket:

- the root `AGENTS.md` for safety, validation, and approval routes;
- `docs/agents/triage-labels.md` for the five `Status` meanings;
- `docs/agents/issue-tracker.md` for local paths, blockers, and update rules; and
- the target file, parent spec, referenced blockers, relevant canonical documentation, and code.

If `docs/agents/triage-labels.md` is missing or does not map all five roles, stop and tell the
user. If the target path is outside the configured initiative structure, stop. Do not invent a path
or status.

## State-only responsibility

Assess exactly one of these state roles:

- `needs-triage`
- `needs-info`
- `ready-for-agent`
- `ready-for-human`
- `wontfix`

Use the meanings in `docs/agents/triage-labels.md`. Keep the recommendation and local tracker draft
limited to the selected state role.

A state recommendation never approves implementation. A requested state, including
`ready-for-agent`, also does not approve implementation.

Never invoke implement automatically.

## Write approval gate

Separate read-only assessment from local tracker writes. Follow
`docs/harness/safety-policy.md`.

- Automatic selection permits reading local work items, inspecting the codebase, and preparing
  drafts without approval.
- Before any tracker write, show the exact file path, `Status` change, and full final comment under
  `## Comments`.
- Ask for explicit approval immediately before writing. Invoking `triage`, accepting the
  assessment, or naming a desired state does not approve an unshown local file change.
- Apply only the approved batch. If the target, content, status, or actions change, show the
  updated preview and ask again.
- Without approval, stop after delivering the recommendation and drafts.

Repository changes are outside this tracker-write gate and require their own route under
`AGENTS.md`.

## Workflow

1. **Confirm the input.**
   - Confirm that the target is a configured local Markdown implementation ticket.
   - Read `docs/agents/triage-labels.md` and stop if its mapping is unavailable or incomplete.

2. **Gather current evidence.**
   - Read the ticket body, `Status`, `Blocked by`, `## Comments`, parent spec, blocker files, and
     every sibling ticket in the same `tickets/` directory.
   - Read prior triage comments so resolved questions are not asked again.
   - Inspect relevant canonical docs and code, including whether the requested behavior already
     exists. Report where you looked and what you found.
   - Do not change files or tracker state while gathering evidence.

3. **Recommend the current state.**
   - Base the recommendation on the ticket and repository evidence.
   - If facts only the reporter can supply are missing, recommend `needs-info` and state the exact
     questions.
   - If a maintainer decision is still required, recommend `needs-triage` and state the decision.
     When focused clarification would help, ask whether to invoke `grill`; do not invoke it or
     `domain-modeling` automatically.
   - Explain why the selected state fits. If the evidence cannot support one state, report what is
     unresolved and stop.

4. **Calculate the frontier and recommend the next route without starting it.**
   - Re-read sibling statuses and blocker files. The current frontier is the lowest-numbered
     `ready-for-agent` ticket whose local Markdown blockers are all `resolved`.
   - If the target is not the current frontier, report the actual frontier or the blockers that
     prevent one. Do not recommend implementation.
   - Only when the target is already `ready-for-agent`, is the current frontier, and the evidence
     supports agent implementation, ask whether to invoke implement and wait for user confirmation.
   - A proposed `ready-for-agent` change is not enough: apply the separately approved tracker
     update, re-read all siblings, and recalculate the frontier before recommending implement.
   - For any other state, recommend only the next action implied by that state and do not propose
     agent implementation.
   - Return only the state evidence, next-route recommendation, and tracker drafts. Leave later
     artifacts and implementation decisions to their own routes.

5. **Prepare the tracker outcome without writing.**
   - Draft the selected `Status` change.
   - For `needs-info`, draft focused questions and preserve facts already established.
   - For `needs-triage`, draft an optional progress comment when it helps.
   - For `wontfix`, draft only the explanatory comment and status change. If a
     durable decision should be recorded, recommend a separate approved change to an existing
     canonical document or ADR; do not create that record during triage.
   - Append every drafted tracker comment under `## Comments` with the AI disclaimer.

6. **Request tracker-write approval.**
   - Show the complete final batch required by the write approval gate.
   - Wait for explicit approval immediately before writing.

7. **Apply and verify.**
   - Apply only the approved tracker changes.
   - Re-read the resulting `Status` and comments from the local file.
   - Recalculate the frontier, then report what changed and any failed or unverified action. Re-enter
     the approval gate before a correction that changes the preview.

## Quick state request

When the user requests a specific state, assess it against the available evidence and explain any
conflict. The request does not approve implementation and does not bypass the tracker-write gate.
Show the exact proposed status and local tracker changes, then ask for write approval.

## Resuming a ticket

Read prior triage notes and new replies, preserve resolved facts, and recommend the current state
from the latest evidence. Do not repeat resolved questions.
