# 설계 문서 작성

## 1. 시작 조건 확인

1. 저장소의 `AGENTS.md`를 읽고 적용하라.
2. 관련 코드, 테스트, 프로젝트 문서, `.dev/specs/`의 기존 설계 문서를 먼저 조사하라.
3. 프로젝트 문서와 실제 코드가 다르면 어느 쪽이 맞는지 한 번에 하나씩 질문하라.
4. 사용자가 직접 새 설계를 요청했다면 새 문서 흐름으로 이동하라.

관련 설계 문서가 이미 있고 사용자가 수정 또는 새 설계를 명시하지 않았다면 다음 형식으로 질문하라.

> `{설계 문서 이름}` 설계 문서가 이미 존재합니다. 해당 설계 문서대로 진행할까요?

- 승인하면 문서를 새로 만들지 말고 `plan` 실행으로 넘겨라.
- 수정을 요청하면 기존 문서를 수정하라.
- 새 설계를 요청하면 새 작업 번호로 문서를 만들라.

## 2. 필요한 정보 수집

- 코드와 문서에서 직접 확인할 수 있는 내용은 사용자에게 묻지 말고 직접 확인하라.
- 설계 결과를 크게 바꾸는 정보만 질문하라.
- 질문은 한 번에 하나만 하라.
- 사용자의 추천 선택지가 있으면 세 개 이하로 제시하고 추천 항목을 표시하라.

설계 문서를 작성하기 전에 다음 내용을 판단할 수 있는지 확인하라.

1. 해결할 문제, 목표와 성공 조건
2. 포함 범위와 제외 범위
3. 주요 구성요소의 책임과 경계
4. 데이터 흐름, 외부 연동과 오류 처리 방향
5. 호환성, 보안, 운영과 되돌리기 어려운 변경의 제약
6. 검증 전략을 바꿀 수 있는 중요한 결정

- 저장소에서 확인할 수 없는 정보가 위 판단을 크게 바꾸면 사용자에게 한 번에 하나씩
  질문하고, 답변을 반영한 뒤 준비 상태를 다시 확인하라.
- 중요한 미해결 문제가 하나라도 남아 있으면 설계 문서를 작성하거나 승인을 요청하지
  말고 질문을 계속하라.
- 사용자가 판단을 명시적으로 위임하면 합리적인 권장안을 선택하고 그 결정을 설계 문서에
  기록한 뒤 진행하라.
- 위 항목을 모두 판단할 수 있을 때만 설계 작성 단계로 이동하라.

## 3. 작업 번호 정하기

새 문서를 만들 때 다음 규칙을 적용하라.

1. Asia/Seoul 기준 오늘 날짜를 `yymmdd`로 구하라.
2. `.dev/specs/`, `.dev/plan/`, `.dev/implementation/`에서 오늘 날짜로 시작하는 문서를 찾으라.
3. 가장 큰 `nn` 다음 번호를 두 자리로 사용하라. 오늘 문서가 없으면 `01`을 사용하라.
4. 작업 내용을 짧고 알아보기 쉬운 파일 이름으로 바꾸라.
5. `.dev/specs/yymmdd-nn-{작업 내용}-design.md`에 저장하라.

기존 문서를 수정할 때는 새 번호나 새 문서를 만들지 마라.

## 4. 설계 문서 작성

문서 맨 위에 다음 정보를 포함하라.

- 상태: `작성 중`
- 작성 날짜와 시간
- 연결된 계획 문서가 있으면 해당 링크

작업에 맞게 항목을 추가하되 다음 항목은 반드시 포함하라.

1. 목적
2. 구조와 책임
3. 데이터 흐름
4. 오류 처리
5. 검증 전략

다음 원칙을 지켜라.

- 설명은 한국어로 작성하고 코드와 기술 이름은 원래 영어를 유지하라.
- 비밀번호, API 키, 접근 토큰, 개인정보를 기록하지 마라.
- 사실, 결정, 아직 남은 위험을 구분하라.
- 변경 이력 목록을 만들지 말고 최신 내용만 유지하라.
- 관련 계획 문서가 생기면 양쪽 문서에 서로의 링크를 추가하라.

## 5. 승인 받기

문서를 저장한 뒤 사용자에게 설계 문서 링크를 보여주고 승인 또는 수정 요청 하나만 질문하라.

- 승인되면 상태를 `승인됨`으로 바꾸고 승인 날짜와 시간을 기록하라.
- 중요한 수정 요청을 받으면 상태를 `작성 중`으로 되돌리고 기존 문서를 수정하라.
- 수정이 끝나면 다시 승인을 요청하라.
- 승인된 뒤 공통 하네스가 `plan`을 실행하도록 넘겨라.
