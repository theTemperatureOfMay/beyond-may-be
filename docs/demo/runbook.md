# Beyond May Be 공모전 데모 Runbook

이 문서는 공모전 현장에서 Beyond May Be의 프런트엔드·백엔드 통합 흐름을 시연하고,
장애가 발생하면 정해진 시간 안에 로컬 API 시연으로 전환하기 위한 운영 절차다.
제품 동작은 [사용자 흐름](../product/user-flow.md), 백엔드 구현과 검증 상태는
[백엔드 MVP 상태](../product/mvp.md), 로컬 실행 방법은 [프로젝트 README](../../README.md)를
정본으로 사용한다.

- 문서 상태: 시연 전 초안
- 목표 시간: 5~7분
- 기본 환경: 배포 환경에서 실행하는 통합 서비스
- 대체 환경: Windows 노트북의 로컬 백엔드·PostgreSQL과 Postman
- 최종 통합 리허설: 미실행

현재 백엔드 MVP 상태에는 `동작` 또는 `데모 검증` 기능이 없다. 따라서 아래 절차는
목표 시나리오이며, 최종 리허설을 통과하기 전에는 실제 시연이 가능하다고 판단하지
않는다.

## 성공 조건

- 노트북의 코스 생성자와 스마트폰의 공유 링크 참여자가 일곱 단계 종단 흐름을
  5~7분 안에 완료한다.
- 단계마다 아래 시연표의 성공 신호를 화면에서 확인한다.
- 운영 담당자가 Health와 로그를 확인하고 장애 발생 후 30초 안에 한 번만 복구를
  시도한다.
- 복구에 실패하면 이미 실행·검증된 로컬 API 시연으로 즉시 전환한다.
- 실제 비밀번호, API 키, 접근 토큰과 실사용자 정보는 화면, 문서, Postman 공용
  Collection과 로그에 노출하지 않는다.

## 역할과 장비

| 역할 | 장비 | 책임 |
|---|---|---|
| 발표자 | 노트북 | 코스 생성자 흐름을 진행하고 제품 이야기를 설명한다. |
| 운영 담당자 | 스마트폰과 운영 화면 | 공유 링크 참여자 흐름, Health·로그 확인과 장애 전환을 담당한다. |

두 장비의 충전 상태와 네트워크를 미리 확인한다. 스마트폰은 위치 권한을 허용하고
공유 링크를 열 수 있어야 한다. 발표 화면에는 운영 콘솔과 비밀값을 띄우지 않는다.

## 배포 환경과 확인 항목

백엔드는 AWS ALB·ECS Fargate·RDS PostgreSQL에 배포하며 상태 확인·로그·복구 절차는
[AWS 배포·운영 절차](../operations/deployment.md)를 따른다. URL과 데모 데이터처럼
아직 확인하지 못한 자리표시자는 실제 리허설 전 갱신하되 자격 정보는 별도 비밀
저장소에서 관리한다.

| 항목 | 현재 값 |
|---|---|
| 데모 release 또는 commit | `<DEMO_RELEASE>` |
| 프런트엔드 URL | `<FRONTEND_URL>` |
| 백엔드 기본 URL | `<BACKEND_BASE_URL>` |
| Health URL | `<DEPLOYED_HEALTH_URL>` |
| 배포 상태 확인 절차 | [AWS 배포·운영 절차](../operations/deployment.md#상태-확인) |
| 로그 확인 절차 | [AWS 배포·운영 절차](../operations/deployment.md#상태-확인) |
| 백엔드 복구 절차 | [AWS 배포·운영 절차](../operations/deployment.md#이전-버전-복구) |
| 데모 데이터 식별 기준 | `<DEMO_DATA_MARKER>` |
| 데모 데이터 사전 초기화 절차 | `<DEMO_DATA_RESET_PROCEDURE>` |

## 최종 리허설 관문

다음 항목을 실제 공모전과 같은 release, 배포 환경, 노트북과 스마트폰에서 확인한다.
하나라도 통과하지 못하면 통합 시연은 준비되지 않은 것이다.

- [ ] 위 자리표시자를 모두 실제 운영 절차로 교체했다.
- [ ] 배포 Health가 HTTP 200과 `UP`을 반환한다.
- [ ] 프런트엔드가 배포 백엔드를 사용하고 운영 콘솔에 오류가 없다.
- [ ] 검수된 장소 데이터가 준비되어 있다.
- [ ] 데모 전용 데이터만 식별해 초기화하는 절차와 대상 건수를 확인했다.
- [ ] 노트북에서 생성한 공유 링크를 스마트폰에서 열고 합류할 수 있다.
- [ ] 스마트폰의 위치 권한과 방문 인증을 확인했다.
- [ ] 실시간 팀 진행 상태가 두 장비에서 일치한다.
- [ ] 일곱 단계 전체를 7분 안에 완료했다.
- [ ] 로컬 PostgreSQL·백엔드가 실행 중이고 Postman 대체 요청이 통과한다.
- [ ] 배포 장애를 가정해 30초 안에 로컬 API 시연으로 전환했다.
- [ ] 발표 화면, 공용 Collection과 로그에 비밀값·실사용자 정보가 없다.

### 단계별 리허설 상태

| 단계 | 성공 신호 | 상태 |
|---|---|---|
| 1. 성향 검사 | 기본 7개 응답 결과로 여행 성향이 표시된다. 동점이면 질문 1개를 추가한다. | `미검증` |
| 2. 닉네임·세션 등록 | 식별코드와 로그인 세션이 발급된다. | `미검증` |
| 3. 기간·장소 선택 | 추천 장소를 선택하고 최소 장소 수 검증을 통과한다. | `미검증` |
| 4. AI 코스 생성·확정 | 생성·수정한 코스가 확정되고 공유 기능이 활성화된다. | `미검증` |
| 5. 공유·팀 합류 | 스마트폰 참여자가 합류하고 양쪽 팀원 목록에 표시된다. | `미검증` |
| 6. 탐험·방문 인증 | 탐험이 시작되고 방문 결과가 양쪽 화면에 반영된다. | `미검증` |
| 7. 여행 기록·밝힌 지도 | 방문 기록과 밝힌 장소가 조회된다. | `미검증` |

코드, 배포 설정이나 외부 연동이 바뀌면 영향받은 단계를 다시 `미검증`으로 되돌리고
같은 환경에서 재시연한다.

## 시연 직전 준비

운영 담당자는 발표 시작 전에 다음 순서로 준비한다.

1. `<DEMO_RELEASE>`가 최종 리허설한 release와 같은지 확인한다.
2. 배포 상태, Health, 프런트엔드와 백엔드 로그를 확인한다.
3. `<DEMO_DATA_RESET_PROCEDURE>`로 `<DEMO_DATA_MARKER>`에 해당하는 데모 데이터만
   초기화하고 대상 건수를 기록한다. 전체 DB와 공유 데이터는 삭제하지 않는다.
4. 검수된 장소 데이터가 유지됐는지 확인한다.
5. 노트북 브라우저를 코스 생성자 시작 화면에 두고 스마트폰 네트워크·위치 권한을
   확인한다.
6. 아래 로컬 대체 환경을 미리 실행하고 Health와 Postman 요청을 확인한다.
7. 발표 화면에서 알림, 운영 콘솔, 비밀값과 개인 정보를 숨긴다.

시연 중에는 DB를 초기화하지 않는다. 상태가 꼬이면 새 데모 사용자를 한 번 만들거나
즉시 로컬 API 시연으로 전환한다.

## 5~7분 통합 시연

| 목표 시각 | 발표자 동작 | 운영 담당자 동작 | 확인할 결과 |
|---|---|---|---|
| 0:00~0:40 | 성향 검사 기본 7개 질문에 답한다. | 화면과 오류 여부를 확인한다. | 여행 성향 결과가 표시된다. |
| 0:40~1:10 | 닉네임을 등록한다. | 식별코드가 화면에만 표시되는지 확인한다. | 세션이 생성되고 다음 단계로 이동한다. |
| 1:10~2:00 | 기간을 정하고 추천 장소를 선택한다. | 추천·선택 오류를 확인한다. | 최소 장소 수를 충족하고 코스 생성이 활성화된다. |
| 2:00~3:10 | AI 코스를 생성해 한 번 수정하고 확정한다. | 지연 시간과 백엔드 상태를 확인한다. | 확정 코스와 공유 링크가 만들어진다. |
| 3:10~4:00 | 공유 링크를 전달하고 팀원 목록을 연다. | 스마트폰으로 링크를 열어 새 사용자로 합류한다. | 두 장비에 같은 팀원이 표시된다. |
| 4:00~5:20 | 탐험을 시작하고 팀 진행 상태를 연다. | 위치 권한을 허용하고 방문 인증을 수행한다. | 방문 결과와 팀 진행 상태가 실시간 반영된다. |
| 5:20~6:20 | 여행 기록과 밝힌 지도를 연다. | 양쪽 결과가 일치하는지 확인한다. | 방문 장소와 기록이 조회된다. |
| 6:20~7:00 | 핵심 가치를 요약하고 시연을 종료한다. | Health와 오류 유무를 최종 확인한다. | 추가 조작 없이 질의응답으로 전환한다. |

세부 기능을 추가로 보여 주기 위해 7분을 넘기지 않는다. 미정 제품 정책은 현장에서
임의로 설명하지 않고 [제품 논의 필요](../product/open-questions.md)의 상태를 따른다.

## 장애 대응과 전환 기준

장애가 발생하면 운영 담당자가 타이머를 시작한다. 아래의 최소 복구를 한 번만
시도하고 30초 안에 성공 신호가 돌아오지 않으면 로컬 API 시연으로 전환한다.

| 증상 | 한 번만 시도할 복구 | 성공 신호 | 실패 시 |
|---|---|---|---|
| 프런트엔드가 열리지 않음 | 페이지를 한 번 새로 고치고 Health를 확인한다. | 화면과 Health가 모두 정상이다. | 로컬 API 전환 |
| 배포 백엔드 Health 실패 | [상태 확인 절차](../operations/deployment.md#상태-확인)를 확인하고 승인된 경우에만 [이전 버전 복구](../operations/deployment.md#이전-버전-복구)를 수행한다. | Health가 200·`UP`이다. | 로컬 API 전환 |
| DB 연결 오류 | 상태와 로그만 확인한다. 시연 중 DB를 재생성하거나 초기화하지 않는다. | 기존 요청이 정상 처리된다. | 로컬 API 전환 |
| AI·지도 외부 연동 지연 | 현재 입력을 유지한 채 해당 요청만 한 번 다시 시도한다. | 같은 단계의 성공 응답이 온다. | 검증된 API 요청 또는 다음 대체 화면으로 전환 |
| 스마트폰 공유 링크·네트워크 실패 | Wi-Fi와 모바일 데이터 중 준비된 다른 연결로 한 번 전환한다. | 참여자 합류 화면이 열린다. | 노트북의 검증된 API 요청으로 합류 결과 설명 |
| 위치 권한·방문 인증 실패 | 스마트폰 권한을 한 번 확인하고 같은 장소에서 다시 시도한다. | 방문 성공과 팀 갱신이 보인다. | 검증된 방문 API 요청으로 전환 |
| 데모 데이터 상태 불일치 | 기존 데이터를 삭제하지 않고 새 데모 사용자를 한 번 만든다. | 시작 화면에서 정상 진행된다. | 로컬 API 전환 |

복구 중 원인을 길게 설명하거나 새로운 명령을 즉석에서 시도하지 않는다. 발표자는
“연결 문제로 준비한 API 시연으로 전환하겠습니다”라고 알리고 제품 설명을 계속한다.

## 로컬 API 대체 시연

로컬 대체 환경은 발표 전에 이미 실행되어 있어야 한다. 장애가 난 뒤 처음 빌드하거나
의존성을 내려받는 것은 대체 절차가 아니다.

### 사전 실행

저장소 루트의 Windows PowerShell에서 실행한다.

```powershell
docker compose up -d postgres
docker compose ps
.\gradlew.bat bootRun
```

`postgres`가 `healthy`이고 <http://localhost:8080/actuator/health>가 HTTP 200과 `UP`을
반환해야 한다. Postman Desktop은 `postman/` Local Folder를 연결하고 공용
Collection의 `baseUrl`을 `http://localhost:8080`으로 사용한다.

### 전환 순서

1. 노트북에서 준비된 Postman 화면으로 전환한다.
2. `System / Health` 요청으로 로컬 서버 상태를 보여 준다.
3. 최종 리허설에서 통과한 요청만 일곱 단계 순서에 맞춰 실행한다.
4. 각 요청의 실제 응답과 저장·재조회 결과를 설명한다.
5. 검증되지 않았거나 Collection에 없는 요청은 즉석에서 만들지 않는다.

현재 공용 Collection에서 확인된 요청은 `System / Health`뿐이다. 핵심 API 요청과
saved example이 추가되고 로컬 리허설을 통과하기 전까지 API 대체 시연은 준비되지
않은 상태다. 토큰과 환경별 값은 Git에서 제외된 개인 Postman environment에서만
관리한다.

## 데모 데이터 관리

- 검수된 장소 데이터는 초기화 대상에서 제외한다.
- 사용자·코스·탐험은 시연마다 새로 만들고 `<DEMO_DATA_MARKER>`로 데모 데이터임을
  식별한다.
- `<DEMO_DATA_RESET_PROCEDURE>`는 삭제 전에 환경과 대상 건수를 보여 주고 데모
  데이터만 처리해야 한다.
- 데이터 초기화는 리허설 또는 시연 전에만 수행하고 시연 중에는 실행하지 않는다.
- 실제 사용자 데이터, 전체 DB, Docker volume과 배포 저장소를 초기화하지 않는다.
- 비밀번호, 토큰, API 키와 개인 정보는 초기화 명령이나 결과 기록에 남기지 않는다.

최종 리허설마다 아래 표에 최신 결과만 유지한다. 실패한 단계는 수정 후 다시 검증하며,
실행하지 않은 항목은 통과로 기록하지 않는다.

| 항목 | 결과 |
|---|---|
| 실행 날짜·시간 | `미실행` |
| release 또는 commit | `미기록` |
| 배포 환경 | `AWS ALB·ECS Fargate·RDS PostgreSQL` |
| 프런트엔드·백엔드 통합 | `미검증` |
| 일곱 단계 완료 | `미검증` |
| 실제 소요 시간 | `미측정` |
| 배포 장애 30초 전환 | `미검증` |
| 로컬 API 대체 시연 | `미검증` |
| 확인한 사람 | `미기록` |
| 남은 문제 | 실제 배포 URL·프런트엔드 환경 미확인, 핵심 API Postman 요청 미준비 |

## 갱신 규칙

- 실제 배포 URL과 프런트엔드 환경이 확정되면 남은 자리표시자를 갱신한다.
- 기능이나 API 계약이 바뀌면 사용자 흐름, 백엔드 MVP 상태, OpenAPI와 Postman 자료를
  먼저 갱신하고 이 문서의 시연 순서와 성공 신호를 맞춘다.
- 코드, 배포 설정, 데모 데이터나 외부 연동이 바뀌면 영향받은 리허설 결과를
  `미검증`으로 되돌린다.
- 리허설에서 실제로 사용하지 않은 복구 절차는 제거한다.
