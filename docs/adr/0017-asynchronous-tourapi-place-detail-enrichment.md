# ADR-0017 추천 응답과 TourAPI 장소 상세정보 보강을 분리한다

> 공개 장소 상세 조회의 동기 보강과 정상 정보 부재 시 안내 문구를 저장하는 정책은
> [ADR-0020](0020-on-demand-place-detail-enrichment.md)이 이 결정의 해당 경계를 부분
> 대체한다. 추천 응답과 비동기 보강을 분리하는 이 결정은 계속 유효하다.

초기 장소와 런타임에 추가된 장소는 설명이나 운영시간이 없을 수 있지만, 추천 요청에서
상세정보를 동기 조회하면 응답 지연과 외부 장애가 핵심 추천을 실패시킬 수 있다. 추천 생성
요청으로 저장한 실제 응답 장소만 내부 비동기 최선 노력 작업으로 보강하고,
PostgreSQL `places`를 계속 런타임 정본으로 사용한다.

### 결정

- `tour_content_id`가 있고 설명이 비어 있는 응답 장소만 `detailCommon2`의 `overview`를
  조회한다.
- 콘텐츠 ID와 콘텐츠 유형 ID가 있고 운영시간이 비어 있는 응답 장소만
  `detailIntro2`의 유형별 운영시간을 조회한다.
- 외부에서 제공된 비어 있지 않은 값만 DB의 빈 필드에 조건부 갱신하며 기존 값은
  덮어쓰지 않는다.
- 현재 추천 조회 API로 저장 결과를 복구하는 재진입에서는 작업을 시작하지 않는다.
- 작업 지연·부분 실패·예약 실패는 현재 응답과 추천 세트를 변경하지 않는다. 외부 키,
  인증 정보, 개인정보와 전체 외부 응답은 로그에 남기지 않는다.
- 별도 공개 API, 자동 재시도, Redis, 메시지 큐와 분산 작업 상태는 도입하지 않는다.

### 검토한 대안

- 추천 응답 전에 상세정보를 동기 조회하는 방식은 최대 15곳의 외부 호출이 응답 시간과
  성공 여부에 결합되므로 사용하지 않는다.
- 내구성 있는 큐와 작업 상태를 두는 방식은 프로세스 종료 시 유실을 막지만 MVP의 부가
  정보 보강에 비해 운영 복잡도가 크므로 사용하지 않는다. 보강 실행 보장이 실제 요구가
  될 때 다시 검토한다.

### 영향

- ADR-0003의 “TourAPI는 초기 수집에만 사용한다”는 제한을 이 사후 보강 범위에서만
  추가로 대체한다. AI가 DB 장소만 선별하고 `places`가 런타임 정본이라는 원칙은 유지한다.
- 첫 추천 응답의 `summary`는 null일 수 있고, 성공한 보강 값은 이후 DB 조회부터 보인다.
- 프로세스가 종료되면 완료되지 않은 보강 작업은 유실될 수 있다.

### 영향 대상

- 변경 유형: `product`, `api`, `data`, `architecture`, `security`
- 변경한 대상: TourAPI 상세 조회 클라이언트, 응답 장소 보강 Service, 빈 필드 조건부
  Repository 갱신, 255자를 넘는 운영시간을 위한 `text` 확장 migration, 추천 생성 후
  비동기 작업 예약, 관련 제품·데이터·아키텍처 정본과 테스트
- 확인했지만 변경하지 않음: 추천 HTTP 응답·오류 계약, TourAPI 설정과 운영 키 주입,
  현재 추천 조회를 통한 저장 진행 복구, 2.2.4 공개 장소 상세 조회
- 확인하지 못함: 실제 TourAPI 운영 응답과 운영 ECS의 비동기 작업 실행 상태
- 미해결: 보강 실행 보장이 필요해질 때의 큐·작업 상태·재시도 정책
- 수정이 필요한 스킬·하네스: 없음

  아키텍처·OpenAPI 설명·Postman과 실제 클라이언트·Service·Repository·migration·테스트를
  대조했다. 전체 119개 테스트, Spotless, build, 제품 지식 베이스·하네스 semantic 검사,
  Postman JSON 파싱과 `git diff --check`가 통과했고 Standards·Spec 코드 리뷰의 남은
  지적은 없다. 실제 TourAPI와 운영 비밀값은 호출하거나 읽지 않았으며 운영 ECS 상태는
  확인하지 않았다.

### 2026-09-20 동일 일정 추천 생성 계약 정렬

- 변경 유형: `product`, `api`, `data`, `architecture`
- 변경한 대상: 추천 생성 POST가 일정과 관계없이 현재 추천 장소·반응 진행을 교체하도록
  Service와 회귀 테스트를 변경하고, Controller OpenAPI 설명·장소 선택 명세·MVP 상태·
  백엔드 아키텍처·Postman·ClueDoc의 생성과 복구 책임을 동기화했다. 생성 응답의 장소
  상세정보 보강은 모든 성공한 생성 요청에 적용하고, 현재 추천 GET 복구는 작업을 시작하지
  않는다는 이 ADR의 핵심 결정은 유지했다.
- 확인했지만 변경하지 않음: 추천 생성의 HTTP 경로·요청·응답·오류·인증 계약,
  `recommendation_sets`의 사용자당 한 행 제약과 스키마, 현재 추천 GET 복구, 기존 Course
  저장 데이터, TourAPI·Groq 클라이언트와 보안·하네스 규칙
- 확인하지 못함: 실제 프런트엔드의 생성 버튼·새로고침·재진입 E2E, 실제 TourAPI·Groq
  응답, Docker를 사용하는 애플리케이션 컨텍스트·Repository 통합 테스트
- 미해결: 저장소의 공개 계약·코드·문서·테스트 사이에 알려진 불일치는 없다. 동일 생성
  POST의 자동 재시도와 영속 멱등성 키는 도입하지 않으며 프런트엔드는 중복 제출을 막는다.
- 검사 근거: 추천 Service·MockMvc 테스트 70개, `spotlessCheck`, 테스트 제외 전체 빌드,
  제품 지식 베이스·하네스 semantic 검사와 Standards·Spec 코드 리뷰가 통과했다. 전체
  테스트는 490개 중 Docker/Testcontainers가 필요한 23개가 환경 때문에 시작되지 못했고,
  이번 변경 관련 실패는 확인되지 않았다.
