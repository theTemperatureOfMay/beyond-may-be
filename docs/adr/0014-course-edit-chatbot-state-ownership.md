# ADR-0014 코스 편집 되돌리기·AI 미리보기는 클라이언트가 소유하고, DRAFT 코스 조회는 소유자 전용 별도 엔드포인트로 분리한다

코스 설계(3.2)에 직접 코스 수정(3.2.2)과 AI 코스 수정 요청(3.2.1, 이하 코스
챗봇)을 구현하면서, 편집 되돌리기 이력과 AI 미리보기를 어디에 보관할지,
미확정(DRAFT) 코스를 어떤 API로 노출할지 결정이 필요했다.

### 배경

두 흐름 모두 "적용 사용자: 닉네임 세션 사용자 (코스 미확정)"으로 DRAFT
`Course`에서만 동작한다. 직접 수정은 순서 변경·삭제 시 되돌리기(↺)를
제공해야 하고, 코스 챗봇은 Groq 응답을 즉시 반영하지 않고 미리보기로 보여준
뒤 사용자가 '이 코스로 변경'을 선택해야 저장된다(최대 2회, `Course.
aiRevisionCount`로 관리). 두 경우 모두 "확정 전 임시 상태"를 어디가
소유하느냐가 핵심이었다. 또한 기존 `GET /api/v1/courses/{courseId}`
(`CourseService.getCourseDetail`)는 CONFIRMED 코스만 반환하며 공유 링크
미리보기를 위해 의도적으로 인증 없이 열려 있어(ADR-0004), 편집 화면이 DRAFT
코스를 조회할 방법이 없었다.

### 결정

- **편집 되돌리기 이력은 프런트엔드가 로컬 상태로 소유한다.** 서버는
  이력 테이블을 두지 않고, 편집 완료 시점의 최종 장소 목록(순서 포함)을
  저장하는 API만 제공한다. ADR-0002·ADR-0008이 가입 전 성향 검사·장소
  스와이프에 적용한 "재접속·공유·기록에 불필요한 화면 상태는 프런트가
  소유한다" 원칙을, 이미 서버에 영속화된 `Course(DRAFT)` 편집에도 동일하게
  확장 적용한다.
- **코스 챗봇의 미리보기는 서버에 저장하지 않는다(stateless).** Groq 응답으로
  만든 미리보기는 응답 DTO로만 반환하고, 사용자가 '이 코스로 변경'을 선택하면
  클라이언트가 그 미리보기 데이터를 그대로 재전송하는 별도 적용 API를 호출해
  실제 저장을 확정한다. `Course.aiRevisionCount`만 서버가 증가시켜 2회
  제한을 관리한다.
- **DRAFT 코스 조회는 소유자 인증이 필요한 별도 엔드포인트로 새로 만든다.**
  기존 `GET /api/v1/courses/{courseId}`(CONFIRMED 전용, 인증 없는 공개 공유
  미리보기)는 그대로 둔다.

### 검토한 대안

- 되돌리기 이력을 서버가 단계별로 저장하는 이력 테이블: 편집 세션마다 쓰기가
  늘고, Course DRAFT 편집이라는 좁은 범위에 비해 과한 구조라 기각했다.
- AI 미리보기를 `Course`/`CoursePlace`에 pending 상태로 임시 저장: 확정 전
  상태를 위한 추가 컬럼·상태 전이가 필요해 복잡도만 늘어 기각했다. stateless
  응답 + 클라이언트 재전송 방식이 기존 DTO 구조로 충분히 표현된다.
- 기존 `GET /api/v1/courses/{courseId}`의 CONFIRMED 제한을 풀어 DRAFT도
  반환: 이 엔드포인트는 의도적으로 인증 없이 열려 있는 공개 공유 미리보기용
  (ADR-0004)이라, DRAFT까지 반환하면 인증되지 않은 요청이 다른 사용자의
  미확정 코스를 볼 수 있어 기각했다.

### 영향

- 코스 편집 중 브라우저를 바꾸거나 새로고침하면 되돌리기 이력은 복구되지
  않는다(서버에는 최종 DRAFT 상태만 남는다) — ADR-0008과 같은 트레이드오프다.
- 코스 조회 API가 두 개로 늘어난다: 공개 CONFIRMED 미리보기(기존)와 소유자
  인증 DRAFT 편집 조회(신규).
