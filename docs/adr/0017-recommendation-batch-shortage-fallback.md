# ADR-0017 추가 추천 회차는 신규 장소를 우선하고 마지막에 싫어요 장소를 재추천한다

추가 추천 회차는 20곳으로 고정한다. 서버는 현재 추천 세트에서 아직 노출하지 않은 활성
DB 장소를 먼저 사용하고, 20곳보다 부족하면 TourAPI 변경분을 한 번 조회해 유효한 신규
장소를 DB에 저장한 뒤 다시 계산한다. 그래도 부족하면 새 장소를 모두 포함하고 현재
좋아요가 아닌 기존 싫어요 장소로 부족분을 채운다.

### 결정

- 싫어요 장소는 신규 후보와 TourAPI 보충으로도 20곳을 만들 수 없을 때만 사용한다.
- 같은 장소의 반복 노출을 제한하기 위해 싫어요 장소는 한 번만 재추천한다.
- 재추천된 장소의 새 반응이 해당 장소의 이전 반응을 대체한다. 이전 회차 요청을 다시
  보내면 이미 만든 다음 회차를 반환하며 같은 회차를 중복 생성하지 않는다.
- 신규 장소와 재추천 가능한 싫어요 장소를 합쳐도 20곳이 되지 않으면 부분 추가 회차를
  만들지 않고 `hasNextBatch=false`, `nextBatch=null`을 반환한다.
- 최초 추천은 외부 실패와 저장된 후보 수에 따라 20곳 미만일 수 있지만, 이후 추가 회차는
  항상 20곳이다. 순서가 있는 기존 ID 배열을 유지하고 별도 회차 테이블이나 migration은
  추가하지 않는다.
- 최초 추천이 0곳이면 빈 상태로 끝낸다. 빈 1회차 반응은 외부 보충이나 추가 회차 생성을
  다시 시작하는 신호로 사용하지 않는다.

이 결정은 모든 노출 장소를 다음 후보에서 제외하던
[ADR-0008](0008-recommendation-batches.md)을 대체한다. 서버가 현재 추천 세트와 확정
반응을 보존하고 회차별로 반응을 받는 상태 소유권 결정은 유지한다.

### 검토한 대안

- 남은 신규 장소만으로 20곳 미만의 추가 회차를 만들면 회차 크기 계약과 평면 ID 배열의
  회차 경계가 깨지므로 사용하지 않는다.
- 싫어요 장소를 제한 없이 반복하면 같은 카드가 무한히 순환할 수 있으므로 장소당 한 번만
  재추천한다.
- 회차별 하위 테이블이나 별도 경계 열은 더 복잡한 반응 이력이 필요해질 때 도입한다.

### 영향 대상과 검사

- 변경 유형: `product`, `api`, `architecture`
- 변경 대상: 장소 선택 기능 명세·사용자 흐름·MVP 상태·백엔드 아키텍처, 추천
  Controller·DTO·Service·오류 코드와 테스트, ADR-0008의 대체 상태
- 확인하지만 변경하지 않는 대상: 인증과 공통 `ApiResponse` 계약, `recommendation_sets`
  스키마, TourAPI·Groq 클라이언트와 비밀값 설정
- 미해결: 없음
- 검사: 2026-08-23 관련 Service·MockMvc 테스트, Spotless, 테스트 제외 빌드, 제품 지식·
  하네스 semantic 검사, Postman JSON과 ClueDoc 링크 검사가 통과했다. 당시 전체 테스트와
  전체 빌드는 삭제된 원본 JSON을 직접 읽던 `TourApiPlaceCatalogMigrationTest` 1개만
  실패했으며, 같은 날 Flyway V8을 정본으로 사용하도록 해당 비교 의존성을 제거했다.
  제거 후 테스트 컴파일·Spotless·테스트 제외 빌드는 통과했고, 컨테이너 테스트 재실행은
  Docker 데몬 무응답으로 완료하지 못했다. `change-impact-review`와 코드 리뷰에서 발견한
  문서 정합성 및 빈 최초 회차 경계 문제는 수정했다.
