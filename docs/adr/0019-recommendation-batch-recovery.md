# ADR-0019 추천 회차는 장소를 중복하지 않고 마지막 부분 회차를 허용한다

현재 추천 조회는 재진입한 사용자가 서버에 확정된 회차별 장소와 반응을 정확히 복구할 수
있어야 한다. 현재 추천 세트는 순서가 있는 장소 ID 배열과 전체 좋아요·싫어요 ID 배열만
저장하므로, 같은 장소를 여러 회차에 노출하면 이전 반응과 아직 반응하지 않은 다음 회차를
구분할 수 없다. 따라서 현재 추천 세트 안에서는 장소를 중복하지 않고, 남은 장소가
20곳보다 적어도 마지막 회차로 제공한다.

### 결정

- 같은 `placeId`는 현재 추천 세트의 한 회차에만 포함한다. 추가 회차 후보에서는 지금까지
  저장한 모든 추천 장소 ID를 제외한다.
- 추가 회차는 미노출 활성 장소를 우선하고, 부족하면 기존 TourAPI 변경분 보충을 한 번
  수행한 뒤 남은 장소를 최대 20곳까지 제공한다. 1~19곳이면 부분 회차로 저장하고 0곳이면
  `hasNextBatch=false`, `nextBatch=null`을 반환한다.
- 20곳 미만 회차는 해당 추천 세트의 최종 회차다. 이후 장소 카탈로그가 바뀌어도 같은 추천
  세트에 새 회차를 붙이지 않는다. 최초 추천이 빈 목록인 경우도 최종 빈 상태로 유지한다.
- 추천 장소 ID 배열은 앞에서부터 20개씩 회차로 나누고 마지막 회차만 20개 미만일 수 있다.
  별도 회차 테이블·경계 열과 migration은 추가하지 않는다.
- 장소 ID가 회차 간 중복되지 않으므로 전체 좋아요·싫어요 ID 배열을 각 회차 장소와
  교집합해 확정 반응과 완료 여부를 복구한다. 현재 카드 위치, 일괄 전송 전 반응과 되돌리기
  이력은 계속 프런트엔드 로컬 상태로 둔다.

이 결정은 싫어요 장소를 다음 회차에 한 번 재추천하던
[ADR-0018](0018-recommendation-batch-shortage-fallback.md)을 대체한다. 현재 추천 세트와
확정 반응을 서버가 보존하고 회차별로 반응을 받는 상태 소유권 결정은 유지한다.

### 검토한 대안

- 싫어요 재추천을 유지하면서 회차별 반응이나 완료 상태를 새로 저장하면 정확히 복구할 수
  있지만, 현재 계약에 필요하지 않은 회차별 저장 구조와 migration이 생기므로 채택하지
  않는다.
- 남은 미노출 장소가 20곳보다 적을 때 모두 버리면 평면 배열 경계는 유지되지만, 마지막
  회차가 20개 미만일 수 있다는 계약과 남은 장소를 제공하려는 제품 목적에 맞지 않아
  채택하지 않는다.
- 부분 회차 뒤에 새 회차를 계속 붙이면 기존 평면 배열만으로 과거 회차 경계를 복원할 수
  없으므로 채택하지 않는다.

### 영향 대상과 검사

- 변경 유형: `product`, `api`, `architecture`
- 변경한 대상: 장소 선택 기능 명세, 기능 명세의 TourAPI 사용표, 사용자 흐름, 제품 논의
  필요, MVP 상태, 백엔드 아키텍처, Postman 안내·컬렉션과 추천
  Controller·DTO·Converter·Service 및 Service·MockMvc 테스트. 현재 추천 조회의
  `places[].summary`는 ADR-0017과 실제 저장 상태에 맞춰 OpenAPI에서도 `string | null`로
  명시했고, 기존 계약의 nullable `thumbnailUrl`도 함께 검증했다.
- 확인했지만 변경하지 않은 대상: 인증과 공통 `ApiResponse` 계약,
  `recommendation_sets` Entity·Repository·Flyway schema, TourAPI·Groq 클라이언트와
  비밀값 설정, 하네스·스킬 규칙과 프런트엔드 로컬 상태의 내부 복구 방식
- 확인하지 못함: 실제 프런트엔드 재진입 E2E, 운영 데이터의 ADR-0018 추천 세트 존재 여부,
  실제 TourAPI·Groq 응답. Docker 데몬이 응답하지 않아 전체 테스트와 테스트를 포함한 전체
  빌드는 실행 단계에서 완료하지 못했다.
- 배포 조건: ADR-0018 방식으로 저장된 현재 추천 세트가 없는 환경에만 배포한다. 회차 간
  중복 ID가 있거나 첫 부분 회차 뒤에 전체 회차가 이어진 기존 세트가 있으면 배포를 멈추고
  초기화 또는 migration을 별도 결정·승인한다. 이번 변경은 운영 데이터를 수정하지 않는다.
- 미해결: 저장소의 공개 계약·코드·문서·테스트 사이에 남은 불일치는 없다. 위 배포 조건에
  걸릴 때 필요한 운영 데이터 처리 방식은 현재 범위 밖의 조건부 후속 결정이다.
- 재검사: 추천 Service·MockMvc 테스트 70개와 OpenAPI nullable 계약 테스트, 전체
  `spotlessCheck`, 테스트 제외 `build`, Postman JSON 파싱, 제품 지식·하네스 semantic 검사,
  ClueDoc 링크 검사가 통과했다. `change-impact-review`의 저장소 정합성 판정은 `통과`이며,
  Docker와 운영·프런트엔드 확인은 위와 같이 별도 기록한다.
