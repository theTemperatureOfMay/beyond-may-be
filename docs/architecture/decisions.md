# Beyond May Be 핵심 의사결정

이 문서는 제품 책임, 도메인 경계, 데이터 소유권과 외부 시스템 경계에 장기적인
영향을 주는 채택된 결정과 그 이유를 기록하는 단일 경량 ADR 기록부다. 현재 적용할
구조는 [백엔드 아키텍처](backend.md), 상세 제품 동작은
[기능 명세](../product/feature-spec.md), 아직 결정되지 않은 사항은
[제품 논의 필요](../product/open-questions.md)를 따른다.

## 운영 규칙

- 채택된 결정만 기록한다. 제안과 미정 사항은 설계 작업 문서 또는 제품 논의 필요에서
  관리한다.
- 결정이 바뀌면 기존 기록을 지우거나 최신 내용으로 고치지 않는다. 새 ADR을 추가하고
  기존 ADR의 상태와 대체 관계를 갱신한다.
- 단순 구현 선택, 기능별 고정값, 현재 구현 상태와 하네스 운영 결정은 기록하지 않는다.
- 다른 정본의 상세 내용을 복사하지 않고 결정에 필요한 배경과 영향을 요약한 뒤
  원문을 연결한다.
- 소급 기록에서 정확한 결정일이나 당시 이유를 확인할 수 없으면 추측하지 않고
  `확인 불가` 또는 `기록되지 않음`으로 표시한다.

상태는 현재 적용 중인 `채택됨`과 새 ADR로 교체된 `대체됨`을 사용한다.

## ADR-001 닉네임·식별코드와 서버 세션으로 사용자를 식별한다

- 상태: 대체됨
- 결정일: 확인 불가
- 기록일: 2026-07-31
- 대체함: 없음
- 대체됨: ADR-007

### 배경

서비스는 별도의 이메일이나 소셜 계정 가입 없이 성향 검사를 마친 사용자가 닉네임을
등록하고 이후 같은 사용 상태로 돌아올 수 있어야 한다. 같은 닉네임은 여러 사용자가
사용할 수 있다.

### 결정

- 내부 식별자는 `User.userId`를 사용한다.
- 사용자가 입력하는 닉네임과 서버가 발급하는 공개 식별코드의 조합으로 간편 로그인을
  제공한다.
- 로그인 상태는 원문 토큰을 저장하지 않는 `UserSession`으로 관리한다.
- 식별코드는 강한 인증 수단으로 간주하지 않으며 로그인 시도 횟수를 제한한다.

### 검토한 대안

이메일, 비밀번호 또는 소셜 로그인 도입 여부와 당시 비교 근거는 기록되지 않았다.

### 영향

- 신규 사용자는 별도 계정 공급자 없이 바로 서비스를 시작할 수 있다.
- 식별코드를 분실하면 계정을 복구할 수 없으므로 발급 시 보관 안내가 필요하다.
- 닉네임만으로 사용자를 식별하거나 인증 성공·실패 이유를 구분해서 노출하면 안 된다.

## ADR-002 임시 화면 상태와 재접속 상태의 소유권을 분리한다

- 상태: 채택됨
- 결정일: 확인 불가
- 기록일: 2026-07-31
- 대체함: 없음
- 대체됨: 없음

### 배경

성향 검사와 장소 스와이프에는 사용자가 작성 중인 화면 상태가 많지만, 추천 결과와
확정 코스처럼 재접속·공유·기록에 필요한 정보도 존재한다.

### 결정

- 가입 전 성향 결과, 현재 카드, 되돌리기 이력과 일괄 전송 전 반응은 프런트엔드 로컬
  상태로 관리한다.
- 사용자 세션, 현재 추천 세트, 좋아요·싫어요 최종 결과, 코스, 탐험과 방문 기록은
  서버가 PostgreSQL에 보존한다.
- 스와이프 반응은 모든 카드를 처리한 뒤 한 번에 서버로 전송한다.

### 검토한 대안

화면 진행 상태 전체를 서버에 저장하는 방식의 비교 근거는 기록되지 않았다.

### 영향

- 화면 전용 상태를 위한 API와 테이블을 만들지 않는다.
- 브라우저를 바꾸면 일괄 전송 전 상태는 복구되지 않을 수 있다.
- 서버에 저장된 추천 결과와 코스는 같은 세션의 재진입과 공유 흐름에서 정본이 된다.

## ADR-003 검수된 장소 DB를 런타임 정본으로 사용한다

- 상태: 채택됨
- 결정일: 확인 불가
- 기록일: 2026-07-31
- 대체함: 없음
- 대체됨: 없음

### 배경

AI 장소 추천, 장소 상세, 코스 생성과 탐험 중 주변 추천은 동일하고 검수된 장소
정보를 사용해야 한다. 지도 경로 계산과 초기 장소 수집은 서로 다른 외부 시스템의
책임이다.

### 결정

- 런타임 장소 정본은 PostgreSQL의 `places`다.
- AI는 DB에 존재하는 장소를 선별하며 신규 장소나 임의 ID를 생성하지 않는다.
- 한국관광공사 OpenAPI는 초기 광주 장소 수집에만 사용한다.
- Kakao Maps API를 통한 지도·경로·거리·이동시간 계산은 프런트엔드가 담당하며
  백엔드는 폴리라인과 계산 결과를 저장하지 않는다.
- 5·18 관련 정보는 AI 생성 문구가 아니라 검수된 장소 설명에 포함한다.

### 검토한 대안

- AI가 런타임에 새로운 장소를 생성하는 방식은 사용하지 않는다.
- 외부 장소 제공자를 런타임 정본으로 사용하는 방식의 비교 근거는 기록되지 않았다.

### 영향

- 추천과 코스에 사용하는 모든 장소 ID는 서버 DB 존재 여부를 검증해야 한다.
- 장소 수집과 검수 절차가 런타임 요청 처리와 분리된다.
- 경로 API가 실패해도 텍스트 코스 목록으로 대체할 수 있지만 서버가 경로 결과를
  복구해 주지는 않는다.

## ADR-004 Course와 Exploration의 생명주기를 분리한다

- 상태: 채택됨
- 결정일: 확인 불가
- 기록일: 2026-07-31
- 대체함: 없음
- 대체됨: 없음

### 배경

코스는 AI 생성 뒤 수정·확정되는 여행 계획이고, 탐험은 확정 코스에 사용자가 합류해
시작·진행·완료하는 실행 단위다. 두 대상은 생성 시점과 변경 규칙이 다르다.

### 결정

- `Course`와 `Exploration`을 별도 Aggregate로 둔다.
- AI 생성 성공 시 `Course(DRAFT)`를 저장하고, 코스 확정 시
  `Exploration(BEFORE)`과 생성자 Participant를 만든다.
- 팀 역할, 참여 상태, 표시 이름과 위치 공유 동의는 별도 Team 쓰기 모델이 아니라
  `ExplorationParticipant`가 소유한다.
- Course 하나에는 전체 생명주기에서 Exploration을 최대 하나만 둔다.

### 검토한 대안

- Course와 Exploration을 하나의 생명주기로 관리하는 방식은 사용하지 않는다.
- 별도 Team Aggregate를 유지하는 방식의 당시 비교 근거는 기록되지 않았다.

### 영향

- 코스 확정과 탐험 시작은 서로 다른 상태 전환이다.
- 다른 참여자가 합류하기 전에는 확정을 취소하고 빈 Exploration을 정리할 수 있다.
- 참여 이탈은 Participant 상태를 바꾸며 기존 방문 기록을 삭제하지 않는다.

## ADR-005 Visit을 방문과 여행 기록의 정본으로 사용한다

- 상태: 채택됨
- 결정일: 확인 불가
- 기록일: 2026-07-31
- 대체함: 없음
- 대체됨: 없음

### 배경

팀 지도 진행 상태, 개인 방문 기록과 밝힌 지도는 모두 참여자의 장소 방문에서
파생된다. 방문 인증에는 위치 검증과 선택적 사진이 필요하지만 원본 위치와 사진
파일을 모두 관계형 DB에 보존할 필요는 없다.

### 결정

- `Visit`을 Participant별 CoursePlace 방문의 정본으로 사용한다.
- 같은 Participant의 동일 CoursePlace 중복 Visit을 허용하지 않는다.
- 서버는 요청 GPS로 거리를 재검증하지만 원본 GPS 좌표는 저장하지 않는다.
- 사진 원본은 객체 저장소에 두고 DB에는 비공개 object key와 표시 순서만 저장한다.
- 여행 기록과 밝힌 지도는 Course, Exploration, Participant, Visit과 VisitPhoto를
  조합한 조회 결과로 제공하며 별도 TravelLog 쓰기 모델을 두지 않는다.

### 검토한 대안

- 별도 TravelLog 쓰기 모델을 유지하는 방식의 당시 비교 근거는 기록되지 않았다.
- 원본 GPS 좌표를 보존하는 방식은 사용하지 않는다.

### 영향

- 팀·개인 진행 상태와 여행 기록이 같은 Visit 데이터에서 계산된다.
- 사진 업로드와 Visit 생성의 실패 경계를 분리해야 한다.
- 객체 업로드 후 DB 저장이 실패하면 객체 삭제를 시도하고 남은 고아 객체를 운영
  정리 대상으로 처리해야 한다.

## ADR-006 MVP에서 분산 상태와 자동 재시도를 도입하지 않는다

- 상태: 채택됨
- 결정일: 확인 불가
- 기록일: 2026-07-31
- 대체함: 없음
- 대체됨: 없음

### 배경

공모전 MVP에는 AI 추천·코스 생성처럼 오래 걸리거나 중복 호출 비용이 있는 요청이
있다. 현재 서버 상태는 PostgreSQL과 프런트엔드 로컬 상태로 관리할 수 있다.

### 결정

- MVP에서 Redis를 사용하지 않는다.
- AI 요청의 서버 영속 멱등성 키를 저장하지 않는다.
- API와 AI 요청을 자동 재시도하지 않는다. 요청 중에는 프런트엔드가 전송 버튼을
  비활성화하고, 실패하면 사용자가 해당 요청만 다시 시도한다.

### 검토한 대안

- Redis를 이용한 분산 상태·캐시·rate limit의 구체적인 비교 근거는 기록되지 않았다.
- 서버 영속 멱등성 키와 자동 재시도는 MVP 범위에서 채택하지 않았다.

### 영향

- 네트워크 중복 요청을 완전히 방지하지 못한다.
- 서버가 여러 인스턴스로 확장될 때 WebSocket 상태와 rate limit 전략을 다시 결정해야
  할 수 있다.
- 재시도 UI는 실패한 요청만 다시 호출하고 사용자의 기존 입력을 유지해야 한다.

## ADR-007 추천 작업 상태는 User 소유이며 인증 구현과 분리한다

- 상태: 채택됨
- 결정일: 2026-08-01
- 기록일: 2026-08-01
- 대체함: 없음
- 대체됨: 없음

### 배경

추천 결과는 사용자가 재접속하거나 다시 인증한 뒤에도 이어서 사용할 수 있는 업무
상태다. 인증 토큰이나 로그인 세션은 만료·교체될 수 있으므로 추천 결과의 소유자와
인증 상태를 같은 데이터 관계로 두면 사용자 상태 복구가 인증 수명에 종속된다.

### 결정

- 현재 추천 세트의 소유자는 `User`다.
- `RecommendationSet.user_id`는 유일하며 사용자마다 현재 추천 세트 하나만 둔다.
- access token, refresh token, 서버 세션 등 구체적인 인증 방식과 저장소는 별도
  인증 설계에서 결정한다.
- 업무 API는 서버가 확인한 현재 `User` 컨텍스트를 사용하며, body나 query의
  사용자·세션 ID만으로 소유자를 결정하지 않는다.

### 검토한 대안

- `UserSession`에 추천 세트를 연결하는 방식은 인증 세션 만료·교체 시 업무 상태
  복구가 끊길 수 있어 채택하지 않는다.
- 여러 추천 작업을 동시에 보존하는 별도 작업 공간은 현재 명세의 사용자별 현재
  추천 세트 하나 요구에 포함되지 않아 도입하지 않는다.

### 영향

- 사용자가 재인증하거나 기기를 바꿔도 같은 사용자의 현재 추천 세트를 조회할 수
  있다.
- 인증 담당 팀이 토큰 또는 세션 저장 방식을 추가해도 추천 세트의 소유 관계는
  바뀌지 않는다.
- 기능명세의 `세션 ID` 문구는 유지하되 실제 전달 방식은 인증·API 계약에서
  확정한다.
