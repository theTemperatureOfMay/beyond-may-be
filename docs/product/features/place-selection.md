# 2. 장소 선택

[전체 기능 명세](../feature-spec.md) · [백엔드 MVP 상태](../mvp.md) · [논의 필요](../open-questions.md)

## 상세 기능

### 2.1 장소 탐색

#### 2.1.1 여행 기간 설정

- 적용 사용자: 닉네임 세션 사용자

##### 상세 동작

- 닉네임 등록 완료 후 또는 확정 코스 없는 세션 진입 시 최초 표시
- 기간 옵션 4종 제공: 당일치기 / 1박 2일 / 2박 3일 / 그 이상(직접 선택)
- 날짜 입력 박스는 옵션과 무관하게 상시 노출·활성화
- 당일치기·1박2일·2박3일 선택 시: 시작일만 선택하면 종료일 자동 계산 (당일치기 = 시작일, 1박2일 = 시작일+1, 2박3일 = 시작일+2)
- 각 옵션 우측에 권장 장소 수 표시 (예: "3~5곳")
- '그 이상' 선택 시: 시작일·종료일 범위 직접 선택
- 날짜 유효성: 시작일 ≤ 종료일, 과거 날짜 선택 불가
- 기간 미선택 시 '다음 · 장소 고르기' 버튼 비활성
- 선택한 기간은 로컬 상태로 보관하며 추천 요청 파라미터로 전달
- 기간 재선택 시 기존 선택 장소 목록은 유지하되 최소 개수 재검증

##### 백엔드 API 계약

- 인증 사용자가 `POST /api/v1/recommendations/sets`로 `travelSchedule`, `startDate`,
  `endDate`를 함께 제출한다. 사용자 ID와 성향 점수는 요청으로 받지 않는다.
- 당일치기는 날짜 차이 0일, 1박 2일은 1일, 2박 3일은 2일이어야 하며 직접 선택은
  3일 이상이어야 한다. 시작일은 요청일보다 과거일 수 없다.
- 성공 응답은 현재 추천 세트 ID, 적용 일정, 최소 선택 장소 수와 현재 반환 회차를
  반환한다.

##### 백엔드·기획 참고

최대 기간 상한은 없다.

날짜에는 장소 운영시간과 휴무일을 반영한다.

당일치기 : 3개
1박 2일 기준 : 5개
2박 3일 기준 : 7개
그 이상 기준 : 20개

#### 2.1.2 AI 추천 장소 목록 조회

- 적용 사용자: 닉네임 세션 사용자

##### 상세 동작

- 기간 설정 완료 시 호출
- 클라이언트는 여행 기간만 보내며, 서버가 인증 사용자에게 저장된 사색러·미식러·예술러·기억러
  점수를 조회한다.
- 서버는 DB에 등록된 장소 풀에서 AI가 선별한 후보를 반환 (AI는 신규 장소를 생성하지 않으며, 반환 ID는 서버가 DB 검증 후 전달)
- 추천 장소는 회차당 최대 20곳 제공
- 회차당 20곳은 사용자의 4개 유형별 비율에 맞춰 유형별 장소 수를 배분
  - 예: 사색러:미식러:예술러:기억러 비율이 4:3:2:1이면 사색 장소 8곳,
    미식 장소 6곳, 예술 장소 4곳, 기억 장소 2곳을 추천
- 기억러 장소는 5·18·민주화 관련 장소로 한정하지 않고 역사 건축물과 역사 장소 등을 대상으로 함
- 현재 회차가 끝났을 때 최소 선택 장소 수를 충족하지 못하면, 아직 노출하지 않은 장소를
  우선한 추천 장소를 최대 20곳 추가로 제공하며 최소 기준을 충족할 때까지 반복한다.
  마지막 1~19곳의 부분 회차 또는 빈 회차 뒤에는 같은 추천 세트에 새 회차를 붙이지 않는다.
- 조회 중 전용 로딩 화면 표시, 경과 시간에 따라 안내 문구 3단계 전환
- 로딩 중 취소 버튼 제공 → 요청 취소 후 2.1.1로 복귀
- API 타임아웃: 30초
- 전체 30초를 초과하면 자동 재시도 없이 `503 Service Unavailable`과
  `RECOMMENDATION503`을 반환한다. 제한 안에서 발생한 TourAPI·Groq timeout은 각각 기존
  DB 후보·규칙 기반 추천으로 복구한다.
- 수신한 장소 데이터를 스와이프 카드 덱(최상단 카드부터 순차 표시) 형태로 렌더링
- 각 카드 구성: 장소 대표 이미지, 장소명, 카테고리 태그, 간단 소개 문구
- 이미지 없는 장소: 기본 플레이스 홀더 이미지 대체
- 오류 처리: 6.2 공통 오류 정책에 따른다
  - 재시도 대상: 추천 장소 조회 API
  - 보조 복귀 지점: 2.1.1 여행 기간 설정
  - 자동 재시도: 없음 (AI 호출 중복 방지)
- AI 추천 실패 시 성향 유형과 여행 기간으로 DB 장소를 선별하는 규칙 기반 폴백을 적용해 같은 회차에 최대 20곳을 반환
- AI 추천과 규칙 기반 폴백 모두 결과가 0개인 경우: 오류가 아닌 6.3.1 빈 상태로 처리하며, "준비 중" 안내 후 전체 장소 목록으로 대체
- 동일 사용자가 재진입하면 동일한 추천 결과 반환 (서버 저장)
- 기간을 변경해 새 추천을 요청하면 서버는 기존 추천 세트 ID를 유지하고 기간·추천
  장소를 덮어쓰며, 새 추천의 좋아요·싫어요 결과는 빈 상태로 초기화
- 최초 유형별 할당량보다 활성 DB 장소가 하나라도 부족하면 광주 변경분
  `KorService2/areaBasedSyncList2`를 최대 한 번 조회한다. 유효한 신규 장소를 DB에
  먼저 저장하고 후보를 다시 계산하며, 외부 실패나 0건 결과는 기존 DB 후보와
  재배분으로 처리한다.
- 서버는 활성 DB 장소를 최대 20곳 사용한다. 유형별 최초 할당량은
  최대 나머지 방식으로 계산하고 동률은 사색러→미식러→예술러→기억러 순으로 정한다.
- 특정 유형의 장소가 부족하면 보유 수까지만 배정한 뒤 원래 성향 점수 비율과 같은
  규칙으로 여유 유형에 반복 재배분한다. 재배분 대상 점수 합이 0이면 위 고정 순서를
  사용한다.
- 후보는 사용자 ID와 여행 시작·종료일을 기준으로 안정적으로 섞고 유형을 교차 배치한다.
  전체 활성 후보가 20곳보다 적으면 가능한 장소만, 후보가 없으면 `200 OK`와 빈 목록을
  반환한다.
- 최종 할당량이 정해지면 유형별 `min(가용 수, 할당량×3)`, 전체 최대 60곳을 Groq
  `openai/gpt-oss-20b`에 전달한다. 네 성향 점수, 할당량, 일정과 후보의 ID·유형·이름·
  카테고리·태그 및 값이 있는 주소·운영시간만 전송하며 사용자 ID와 인증·개인정보는
  전송하지 않는다.
- AI는 카테고리·태그 다양성, 짧은 일정의 주소 기준 근접성, 긴 일정의 지역 분산,
  제공된 운영시간 적합성과 유형 혼합을 고려한다. 운영시간이 없다는 이유만으로 제외하거나
  감점하지 않는다.
- Groq는 strict JSON Schema로 순서가 있는 `placeIds` 배열 하나만 반환한다. 서버는 후보
  포함 여부, 중복, 저장 직전 DB 존재·활성 상태, 목표 수와 유형별 할당량을 전부 검증한다.
  하나라도 어긋나거나 최대 20초의 호출이 실패하면 AI 결과 전체를 버리고 위 안정적인
  셔플·유형 교차 배치 결과를 사용하며 자동 재시도하지 않는다. 목표가 0이면 호출하지 않는다.
- 새 추천 세트를 저장하거나 기간 변경으로 다시 생성한 경우에만, 현재 응답의
  `batch.places`에 실제 포함된 장소를 응답과 분리된 내부 비동기 작업으로 보강한다.
  같은 일정으로 저장된 추천을 반환하는 재진입에서는 보강 작업을 다시 시작하지 않는다.
- `tour_content_id`가 있고 설명이 비어 있으면 `detailCommon2`의 `overview`를,
  콘텐츠 ID와 콘텐츠 유형 ID가 있고 운영시간이 비어 있으면 `detailIntro2`의 유형별
  운영시간을 조회한다. 비어 있지 않은 값은 DB의 빈 필드에 조건부 갱신하고, 정상 응답에
  값이 없거나 조회 식별자가 없으면 `상세 설명 정보 없음`·`운영시간 정보 없음`을 저장해
  재호출을 막는다. 실제 외부 오류가 발생한 필드는 비워 두며 기존 값은 덮어쓰지 않는다.
- 상세 보강의 지연·부분 실패·작업 예약 실패는 이미 저장한 추천과 현재 HTTP 응답을
  변경하지 않는다. 별도 공개 API, 자동 재시도, Redis, 메시지 큐와 분산 작업 상태는
  두지 않으며 프로세스가 종료되면 아직 끝나지 않은 작업은 유실될 수 있다.

##### 백엔드 API 계약

- 인증 사용자는 Path·Query·Body 없이 `GET /api/v1/recommendations`로 자신의 현재 추천
  세트 하나를 조회한다. 같은 사용자로 재인증하면 같은 `recommendationId`를 조회한다.
- 응답은 일정, `batchSize=20`, 기간별 최소 선택 수, 저장된 전체 좋아요 수와 준비 여부,
  지금까지 생성된 `batches`를 반환한다. 추천 ID 배열을 앞에서부터 최대 20개씩 나누며
  마지막 회차만 20개 미만일 수 있고 같은 장소 ID는 회차 간 반복하지 않는다.
- 각 회차는 현재 응답 가능한 `places`, 그 장소 중 서버에 확정된 `likedPlaceIds`·
  `dislikedPlaceIds`, 보이는 장소가 모두 확정됐는지 나타내는 `completed`를 반환한다.
  삭제·비활성 장소는 응답과 회차별 반응 배열에서 제외하지만 `selectedPlaceCount`는 저장된
  전체 좋아요 수다.
- `places[].summary`는 저장된 장소 설명을 반환하는 `string | null`이다. 새 장소의 비동기
  상세 보강이 끝나지 않았거나 실패한 경우 `null`일 수 있고, 성공한 보강 값은 이후 조회부터
  반환한다. `places[].thumbnailUrl`도 저장된 대표 이미지가 없으면 `null`이다.
- 현재 카드 위치, 일괄 전송 전 좋아요·싫어요와 되돌리기 이력은 응답하지 않는다. 새로 고침
  전 로컬 반응의 보존·복구는 프런트엔드 책임이며 서버는 로컬 상태 병합 규칙을 정하지 않는다.
- 인증 정보가 없거나 만료되면 401, 현재 추천 세트가 없으면 404, 조회 실패는 500을 반환한다.

##### 백엔드·기획 참고

추천 풀 구성 → AI가 DB에서 선별 (결정 완료)

추천 제공 수 → 회차당 최대 20곳, 최소 선택 기준을 충족할 때까지 추가 회차 제공

추천 요청은 최종 성향 하나가 아니라 4개 유형별 비율과 여행 기간을 사용

20곳 배분 시 소수점·동률·후보 부족 재배분 방식은 위 규칙으로 확정했다.

TourAPI 신분류체계 대분류는 `NA→THINKER(자연 관광)`, `FD→FOODIE(음식)`,
`VE→ARTIST(문화 관광)`, `HS→REMEMBERER(역사 관광)`로 연결한다. `AC`, `EV`,
`EX`, `LS`, `SH`와 숙박은 추천 풀에서 제외한다. 기억러는 5·18 관련 장소로
한정하지 않고 역사 건축물과 역사 장소를 포함한다.

관광 장소·분류 데이터 준비 시 `KorService2/ldongCode2`,
`KorService2/lclsSystmCode2`, `KorService2/areaBasedList2`를 최초 수집에 사용한다. 추천
요청에서는 최초 유형별 할당량이 부족할 때 `KorService2/areaBasedSyncList2`로 광주
`areaCode=5`, 법정동 권역 `lDongRegnCd=12`, `showflag=1`, 2026-08-21 이후 변경분의
첫 페이지를 최대 200건 한 번만 조회하고 추가 페이지와 자동 재시도는 사용하지 않는다.

중심관광지 보조 순위는 `LocgoHubTarService1/areaBasedList1`로 수집한다.
신규 응답은 콘텐츠 ID·장소명·지원 대분류·주소·좌표가 모두 유효할 때만 저장하며,
빈 설명·운영시간·썸네일은 `null`로 둔다. 기존 콘텐츠 ID는 수정하지 않는다. 이 제한된
런타임 보충 경계는 [ADR-0015](../../adr/0015-tourapi-shortage-refill.md)를 따른다.
신규 장소의 여행 성향은 신분류 L1로 결정하고, 화면용 `category`는 로컬 매핑에서 확인되는
가장 구체적인 명칭(L3→L2→L1), `tags`는 사용 가능한 L1·L2·L3 명칭을 순서대로 저장한다.
추천 요청 중 `lclsSystmCode2`를 다시 호출하지 않는다.

상세정보 사후 보강은 현재 추천 응답에 포함된 장소만 대상으로 한다. 최초 응답의 소개는
`null`일 수 있으며, 보강된 값은 이후 DB 조회부터 사용할 수 있다. 2.2.4 상세 조회 시에도
값이 비어 있으면 필요한 TourAPI만 동기 호출해 저장한 뒤 같은 응답에 포함한다. 추천 응답
분리는 [ADR-0017](../../adr/0017-asynchronous-tourapi-place-detail-enrichment.md), 상세 조회
경계는 [ADR-0020](../../adr/0020-on-demand-place-detail-enrichment.md)을 따른다.

AI 실패 시 규칙 기반 폴백 → 적용

#### 2.1.3 스와이프 안내 표시

- 적용 사용자: 명세에 별도 기재 없음

##### 상세 동작

- 스와이프 화면 첫 진입 시 1회만 전체 화면 안내 표시

### 2.2 장소 스와이프

#### 2.2.1 장소 스와이프 — 좋아요

- 적용 사용자: 닉네임 세션 사용자

##### 상세 동작

- 카드 덱 최상단 카드를 오른쪽으로 스와이프하거나 하트 버튼 클릭 시 동작
- 해당 장소를 '선택 장소 목록'에 추가하고 하단 카운터 즉시 +1 업데이트
- 카드가 오른쪽으로 날아가는 애니메이션 후 다음 카드 표시
- 화면 상단에 진행률 표시 (현재 / 전체)

##### 백엔드·기획 참고

추천 장소 제공 수 → 회차당 20곳

#### 2.2.2 장소 스와이프 — 싫어요

- 적용 사용자: 닉네임 세션 사용자

##### 상세 동작

- 카드 덱 최상단 카드를 왼쪽으로 스와이프하거나 X 버튼 클릭 시 동작
- 해당 장소를 선택 목록에 추가하지 않고 다음 카드로 전환
- 카드가 왼쪽으로 날아가는 애니메이션 후 다음 카드 표시
- 넘긴 장소를 포함해 이미 노출한 장소는 같은 추천 세트의 다음 회차에 다시 표시하지 않는다.
- 현재 회차의 모든 카드 스와이프가 끝나면 프런트엔드가 해당 회차의 좋아요·싫어요 장소 ID 전체를 서버에 한 번 일괄 전송
- 현재 회차 소진 시 최소 선택 장소 수를 충족하지 못하면 아직 노출하지 않은 장소를
  우선한 다음 추천을 최대 20곳 요청하고 스와이프를 계속 진행
- 최소 선택 장소 수를 충족한 상태에서 현재 회차를 소진하면 선택 완료를 유도
- 더 제공할 장소가 없으면 "더 이상 추천 장소가 없습니다" 빈 상태를 표시 (6.3.1 참조)

##### 백엔드 API 계약

- 인증 사용자는 `POST /api/v1/recommendations/{batchNumber}/reactions`로 현재 회차의
  `likedPlaceIds`와 `dislikedPlaceIds` 전체를 전송한다. 두 배열은 필수이며 빈 배열을
  허용한다.
- 회차의 모든 장소 ID는 두 배열 중 정확히 하나에 있어야 한다. 배열 내부 중복,
  배열 간 교집합, 누락과 회차 외 ID는 400으로 거부한다.
- 같은 회차를 다시 전송하면 해당 회차의 기존 반응만 최종 배열로 교체한다. 전체 좋아요가
  기간별 최소 수에 도달하면 `selectionReady=true`와 `nextBatch=null`을 반환한다.
- 최소 수에 못 미치면 아직 반응하지 않은 기존 다음 회차를 우선 반환한다. 모든 저장 회차가
  끝났다면 활성 DB 장소에서 이미 노출한 ID를 제외해 새 후보를 계산한다. 새 후보가 20곳
  미만이면 기존 `areaBasedSyncList2` 변경분 조회를 한 번 실행하고, 유효한 신규 장소를 DB에
  저장한 뒤 다시 계산한다.
- OpenAPI 보충 뒤 남은 미노출 장소가 1~19곳이면 모두 부분 회차로 저장해 반환한다. 이 회차는
  최종 회차이며 이후 카탈로그가 바뀌어도 같은 추천 세트에 새 회차를 추가하지 않는다.
  남은 장소가 0곳이면 `selectionReady=false`, `hasNextBatch=false`, `nextBatch=null`을
  반환한다. 싫어요 장소는 부족분으로 재추천하지 않는다.
- 최초 추천이 빈 목록이면 빈 1회차 반응을 보내도 추가 회차를 만들지 않고 같은 빈 상태를
  반환한다.
- 저장된 장소가 삭제됐거나 비활성이어서 응답에서 제외된 경우에는 현재 응답에 보이는 장소
  ID 전체만 좋아요·싫어요로 분할해 전송할 수 있다.
- 현재 추천이나 회차가 없으면 404, AI 선별 중 기간·회차 구성이 바뀌면 409를 반환한다.
  자동 재시도와 서버 영속 멱등성 키는 사용하지 않는다.

##### 백엔드·기획 참고

좋아요·싫어요는 확정 반응으로 저장한다. 다음 회차는 기존 성향·기간 추천 규칙을
재사용하며 반응 기반 별도 재랭킹은 하지 않는다. 회차 간 장소 중복 금지와 최종 부분 회차는
[ADR-0019](../../adr/0019-recommendation-batch-recovery.md)을 따른다.

서버 전송 시점 → 추천 회차별 전체 스와이프 종료 후 한 번 일괄 전송

프런트엔드는 각 회차의 실제 진행률 분모로 `batchSize`가 아니라 `places.length`를 사용한다.
최종 회차가 완료됐는데 `selectionReady=false`이면 더 제공할 후보가 없는 상태로 처리한다.

#### 2.2.3 되돌리기

- 직전 스와이프 1건을 취소하여 해당 카드를 덱 최상단으로 복귀

##### 백엔드·기획 참고

#### 2.2.4 장소 상세 보기

- 적용 사용자: 닉네임 세션 사용자

##### 상세 동작

- 카드 영역을 스와이프 제스처 없이 탭하거나, 선택 목록에서 장소명 클릭 시 하단 시트 표시
- 표시 항목: 대표 이미지, 장소명, 주소, 운영시간, 카테고리 태그, 상세 설명, 5.18 연관 의미(해당 시)
- 운영시간 정보 없는 장소: "운영시간 정보 없음" 텍스트 표시
- 상세 설명 정보 없는 장소: "상세 설명 정보 없음" 텍스트 표시
- 5·18 연관 정보는 사전 검수된 고정 텍스트만 사용하며 AI 생성 문구를 사용하지 않는다
- 상세 화면 내에서 좋아요·싫어요 버튼 활성화하여 스와이프와 동일한 동작 수행
- 4.4.2(탐험 지도 내 장소 상세)와 동일 컴포넌트를 재사용하며, 노출 맥락에 따라 하단 액션 버튼만 분기

##### 백엔드·기획 참고

공용 컴포넌트 계약

- 인증 사용자는 `GET /api/v1/places/{placeId}`로 활성 장소의 카탈로그 상세를 조회한다.
  응답은 장소 ID·이름·카테고리·여행 성향·태그·주소·좌표·운영시간·설명·썸네일을
  포함한다. 방문 여부와 액션 버튼 활성 상태는 탐험·방문 API와 클라이언트 GPS 상태를
  조합한다.
- 서버는 저장값을 먼저 사용한다. 설명이나 운영시간이 비어 있으면 각각
  `detailCommon2.overview`, `detailIntro2`의 콘텐츠 유형별 운영시간을 동기 조회하고,
  빈 필드에만 저장한 뒤 다시 읽어 같은 응답에 포함한다.
- TourAPI가 정상 응답했지만 값이 없거나 필요한 콘텐츠 식별자가 없으면
  `상세 설명 정보 없음`·`운영시간 정보 없음`을 저장하고 반환한다. 이 문구는 재호출 방지
  표식이므로 별도 상태 열을 두지 않는다.
- TourAPI 연결·timeout·HTTP/API·파싱 오류나 필요한 서비스 키 부재는 DB의 빈 값을
  유지하고 `503 Service Unavailable`·`PLACE503`을 반환한다. 다음 상세 요청은 비어 있는
  필드만 재시도한다. 장소가 없거나 비활성이면 `404 Not Found`·`PLACE404`다.
- TourAPI `overview`는 일반 장소 설명이다. 5·18 연관 의미는 서버나 AI가 만들지 않고
  사람이 검수해 기존 `description`에 저장한 문구만 사용하며, 저장된 설명은 외부 값으로
  덮어쓰지 않는다.
- 썸네일은 저장값 또는 `null`을 반환하고 이번 보강 대상에 포함하지 않는다.

### 2.3 선택 관리

#### 2.3.1 선택 장소 목록 확인

- 적용 사용자: 닉네임 세션 사용자

##### 상세 동작

- 화면 하단 고정 바 또는 탭의 '내가 고른 장소 (N개)' 클릭 시 선택 목록 패널 표시
- 목록 구성: 장소 썸네일, 장소명, 카테고리 태그, 개별 삭제(X) 버튼
- X 버튼 클릭 시 해당 장소를 목록에서 제거하고 카운터 -1 업데이트
- 목록 내 장소명 클릭 시 2.2.4 장소 상세 표시
- 선택 장소 0개 상태: '선택 완료' 버튼 비활성화
- 최소 선택 장소 수 미달 시: "장소를 N개 이상 골라주세요" 안내 및 버튼 비활성
- 삭제로 최소 개수 미달이 되는 경우 삭제는 허용하되 버튼만 비활성 처리

##### 백엔드·기획 참고

당일치기 : 3개
