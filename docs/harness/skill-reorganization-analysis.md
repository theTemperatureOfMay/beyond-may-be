# 프로젝트 스킬 재구성 분석 기록

상태: **분석 기록 / 결정 반영됨**
기록일: 2026-08-03
반영일: 2026-08-07
대상: `.agents/skills`와 이를 연결하는 `.claude/skills`

## 1. 목적과 범위

이 문서는 현재 설치된 스킬을 비슷한 기능별로 묶고, 각 스킬의 공통점·차이점·경계를 기록해 이후 재구성 설계의 입력으로 사용한다. 이 문서 자체는 어떤 스킬을 삭제·통합·이름 변경할지 결정하지 않는다.

이번 기록에서 확인한 범위는 다음과 같다.

- `.agents/skills`의 스킬 집합
- `skills-lock.json`의 설치 출처와 잠금 상태
- `.claude/skills`의 현재 연결 상태
- 저장소 공통 규칙과 문서 라우팅을 정의하는 `AGENTS.md`
- 하네스 완료 기준·영향 지도·운영 문서
- GitHub 이슈 트래커와 도메인 문서 소비 규칙
- 기존 사용 안내인 [프로젝트 AI 스킬 사용 안내](skill-catalog.md)

## 2. 분류 기준

스킬 이름이나 공급자보다 실제 계약을 기준으로 비교했다.

| 축 | 확인할 내용 |
| --- | --- |
| 목적 | 어떤 문제를 해결하는가 |
| 호출 시점 | 사용자가 어떤 상황에서 호출하는가 |
| 산출물 | 대화, 계획, 코드, 문서, 이슈, PR 등 무엇을 남기는가 |
| 권한과 부작용 | 읽기 전용, 저장소 쓰기, 외부 쓰기 중 어디까지 하는가 |
| 생명주기 | 단발성 판단인지, 진행 단계인지, 반복 세션인지 |
| 프로젝트 적합성 | Java/Spring/Gradle/PowerShell과 저장소 하네스 규칙에 맞는가 |

따라서 같은 주제를 다루더라도 산출물·권한·호출 시점이 다르면 우선 별도 스킬로 보았다. 반대로 이름이 달라도 같은 계약을 반복하면 통합 후보로 보았다.

## 3. 기능별 그룹

### 3.1 요구사항 명확화와 의사결정 검증

대상: `interview`, `grilling`, `grill-me`, `grill-with-docs`, `batch-grill-me`, `domain-modeling`, `to-questionnaire`

공통점은 모호한 요구사항이나 결정을 질문으로 드러내고, 빠진 전제·충돌·위험을 확인한다는 것이다.

| 스킬 | 고유 역할 | 주요 경계 |
| --- | --- | --- |
| `interview` | 프로젝트 규칙에 맞춰 한 번에 한 질문씩 목적·범위·제약·성공 조건을 구체화한다. | 구현하지 않으며, 일반적인 압박 토론보다 요구사항 수집에 가깝다. |
| `grilling` | 계획·결정·아이디어의 약점을 한 질문씩 집요하게 검증한다. | 프로젝트 문서에 기록하는 역할은 기본 계약이 아니다. |
| `grill-me` | `grilling`을 호출하기 위한 얇은 진입점이다. | 독자적인 분석·산출물 계약이 거의 없다. |
| `grill-with-docs` | 질문을 통해 검증하면서 `CONTEXT`·ADR 등 도메인 기록까지 갱신한다. | 대화만 필요한 경우에는 과하다. |
| `batch-grill-me` | 질문을 한 번에 묶어 라운드별로 검증한다. | 저장소 인터뷰의 “한 응답에 한 질문” 규칙과 충돌할 수 있다. |
| `domain-modeling` | 용어·도메인 모델·유비쿼터스 언어와 ADR 필요성을 정리한다. | 주 인터뷰어라기보다 도메인 기록과 의미 경계를 관리한다. |
| `to-questionnaire` | 외부 지식 보유자에게 비동기적으로 답할 질문지를 만든다. | 실시간 의사결정 인터뷰와 생명주기가 다르다. |

재구성 후보:

- 질문 기반 명확화의 공통 핵심을 하나의 `clarify-decision` 계열로 정리할 수 있다.
- `one-question`, `batch`, `project-docs`는 모드 또는 어댑터 후보지만, 사용자 경험과 승인 흐름이 달라 실제 통합 전 검증이 필요하다.
- `domain-modeling`과 `to-questionnaire`는 각각 도메인 기록과 비동기 질문지라는 고유 산출물이 있어 완전 통합보다 공통 참조 문서 공유가 안전하다.

### 3.2 설계·계획·구현 전달

대상: `ask-matt`, `plan`, `to-spec`, `to-tickets`, `wayfinder`, `implement`

공통점은 아이디어나 요청을 실행 가능한 결과로 옮기는 생명주기의 일부를 담당한다는 것이다. 다만 서로 다른 단계의 산출물을 만들므로 하나의 거대 스킬로 합치면 호출 경계와 승인 경계가 흐려진다.

| 스킬 | 고유 역할 | 주요 경계 |
| --- | --- | --- |
| `ask-matt` | 사용자의 요청을 적절한 Matt 계열 스킬로 라우팅한다. | 자체 산출물보다 진입점·분류가 핵심이다. |
| `plan` | 일반 구현 요구사항과 실제 저장소를 대조해 구현 체크리스트를 만든다. | 큰 작업의 결정 지도나 코드를 만들지 않는다. |
| `to-spec` | 대화와 코드 이해를 제품·구현 결정을 포함한 GitHub spec으로 합성한다. | Issue는 구현 목표이며 현재 구현 상태의 정본이 아니다. |
| `to-tickets` | 수직 슬라이스 티켓과 의존·차단 관계를 만들어 실행 단위로 쪼갠다. | 하나의 상세 설계 문서나 단순 이슈 등록과 다르다. |
| `wayfinder` | 크고 불명확한 작업의 결정·탐색 지도를 여러 세션에 걸쳐 유지한다. | 최종 설계·계획·티켓 자체를 대체하지 않는다. |
| `implement` | 승인된 작업을 코드·테스트·검증까지 실행한다. | 현재 원문에 커밋 지시가 있어 저장소의 “사용자 요청 없이는 커밋하지 않음” 규칙과 충돌한다. 또한 프로젝트 라우팅 용어 보강이 필요하다. |

재구성 후보:

- 각 단계를 유지하되, 승인·산출물·정본·검증을 공통 생명주기 계약으로 맞추는 방향이 우선이다.
- `ask-matt`는 코어 작업 스킬이 아니라 라우터 또는 사용 안내 진입점으로 분리하는 편이 명확하다.
- `plan → implement → code-review`의 일반 구현 흐름과 `wayfinder → to-spec → to-tickets → implement`의 큰 작업 흐름을 명시적으로 구분해야 한다.
- `wayfinder`는 장기 탐색 상태가 필요한 큰 작업에서만 사용하도록 선택적 진입점으로 두는 후보이다.

### 3.3 코드 설계·진단·품질

대상: `codebase-design`, `improve-codebase-architecture`, `diagnosing-bugs`, `tdd`, `prototype`, `code-review`, `resolving-merge-conflicts`

공통점은 코드 변경의 구조적 품질·원인·검증 가능성을 다룬다는 것이다. 하지만 실행 전 설계, 결함 원인 규명, 실험, 변경 후 검토, Git 상태 복구라는 서로 다른 위험 지점을 담당한다.

| 스킬 | 고유 역할 | 주요 경계 |
| --- | --- | --- |
| `codebase-design` | 깊은 모듈·인터페이스·seam·AI 탐색 가능성의 설계 어휘를 제공한다. | 전체 코드베이스를 자동 개선하는 실행 스킬이 아니다. |
| `improve-codebase-architecture` | 코드베이스를 조사해 구조 개선안을 HTML 보고서로 만들고 필요하면 질문으로 검증한다. | 특정 버그의 재현·수정 루프와 다르다. |
| `diagnosing-bugs` | 재현 가능한 실패부터 원인, 최소 수정, 회귀 검증까지 반복한다. | 기능 설계나 일반적인 사후 리뷰가 주 목적이 아니다. |
| `tdd` | 실패 테스트 → 최소 구현 → 정리의 개발 규율을 적용한다. | 테스트 규율이지 독립적인 요구사항·아키텍처 산출물은 아니다. |
| `prototype` | 설계 질문에 답하기 위한 버리는 실험을 만든다. | 운영 코드 구현이나 완료 기능을 만들지 않는다. |
| `code-review` | 기준점 이후 변경을 Standards와 Spec 두 축으로 읽기 전용 검토한다. | 진단·구현·머지 충돌 해결을 대신하지 않는다. |
| `resolving-merge-conflicts` | 진행 중인 merge/rebase 충돌을 해결한다. | 일반 코드 수정이나 리뷰 스킬로 확장하지 않는다. |

재구성 후보:

- `codebase-design`을 공통 참조 어휘로 사용하고, `improve-codebase-architecture`가 이를 소비하도록 연결할 수 있다.
- `diagnosing-bugs`와 `tdd`는 회귀 시험 계약을 공유할 수 있지만, 전자는 원인 규명 생명주기이고 후자는 구현 방식이므로 분리한다.
- `implement` 완료 후 `code-review`를 연결하고, 설계 질문이 불확실할 때만 `prototype`을 앞에 둔다.

### 3.4 하네스·거버넌스·스킬 품질

대상: `harness-audit`, `change-impact-review`, `setup-skills`, `git-guardrails-claude-code`, `writing-great-skills`

공통점은 제품 기능보다 에이전트 작업 환경과 변경 안전성을 관리한다는 것이다.

| 스킬 | 고유 역할 | 주요 경계 |
| --- | --- | --- |
| `harness-audit` | 완료 기준에 따라 프로젝트 하네스를 읽기 전용 평가하고 점수·근거·개선 우선순위를 보고한다. | 평가만 하며 자동 수정하지 않는다. |
| `change-impact-review` | 변경된 정본·문서·코드·테스트·하네스의 영향과 불일치를 읽기 전용으로 확인한다. | 전체 하네스 점수 평가가 아니다. |
| `setup-skills` | 엔지니어링 스킬 설치·연결 등 초기 환경 구성을 담당한다. | 일상적인 스킬 튜닝·정합성 검토와 다르다. |
| `git-guardrails-claude-code` | Claude Code에 위험한 Git 명령을 차단하는 훅을 설치한다. | 단순 Git 사용 안내가 아니라 실제 설정 변경이다. |
| `writing-great-skills` | 스킬의 트리거·진입점·진행·참조·검증 품질을 작성 관점에서 점검한다. | 프로젝트 하네스 전체의 운영 점수나 제품 변경을 다루지 않는다. |

재구성 후보:

- 읽기 전용 감사(`harness-audit`, `change-impact-review`)와 설정 변경(`setup`, `git-guardrails`)을 권한 기준으로 분리한다.
- `harness-diagnostics` 전역 스킬은 프로젝트 스킬로 복제하지 않고, 프로젝트 하네스에서는 그 결과를 소비하는 로컬 감사·운영 문서만 유지하는 경계가 필요하다.
- 스킬 작성 규칙은 실행 스킬에 복사하기보다 공통 참조로 두어 중복 지시를 줄이는 편이 낫다.

### 3.5 GitHub 이슈·PR·작업 추적

대상: `gh-create-issue-from-template`, `triage`, `gh-create-project-pr`

직접적인 공통점은 GitHub라는 외부 시스템에 상태나 산출물을 기록한다는 점이다. 외부 쓰기이므로 저장소 규칙의 이슈 템플릿·라벨·PR 규칙과 승인·최종 대상 확인을 공유해야 한다.

| 스킬 | 고유 역할 | 주요 경계 |
| --- | --- | --- |
| `gh-create-issue-from-template` | 저장소 이슈 템플릿과 제목·섹션·체크박스·이모지를 보존해 이슈를 만든다. | 이슈 상태 분류나 PR 게시를 담당하지 않는다. |
| `triage` | 기본 triage 라벨과 정보 부족·준비 상태를 기준으로 이슈를 분류한다. | 새 이슈의 본문 작성이나 코드 구현과 다르다. |
| `gh-create-project-pr` | 프로젝트 제목 규칙과 PR 템플릿으로 Draft PR을 만들고 CI·JaCoCo artifact를 확인한다. | 일반 이슈 등록과 다르며, 사용자의 명시적 PR 요청이 필요하다. |

인접 스킬과의 차이:

- `to-spec`는 제품 명세를 GitHub에 게시하고, `to-tickets`는 실행 가능한 티켓 집합을 게시한다.
- `wayfinder`는 의사결정 지도를 유지하며, GitHub는 그 결과를 외부 작업 항목으로 남기는 어댑터가 될 수 있다.
- `setup-skills`는 설치·환경 구성이지 작업 추적이다.

재구성 후보:

- 이 그룹은 공통 `issue-tracker` 참조 문서 또는 외부 쓰기 어댑터를 공유한다.
- 이슈 생성·triage·PR은 트리거와 완료 조건이 명확하므로 하나로 합치기보다 외부 쓰기 전 확인 규칙만 통합한다.

### 3.6 세션 인계

대상: `handoff`, `claude-handoff`

공통점은 현재 작업의 맥락·결정·다음 작업을 다른 세션이나 다른 에이전트가 이어받을 수 있게 하는 것이다.

| 스킬 | 고유 역할 | 주요 경계 |
| --- | --- | --- |
| `handoff` | 작업 맥락을 임시 파일 등으로 정리해 다음 세션에 전달한다. | 특정 CLI 실행 없이 인계 자료를 만드는 데 초점을 둔다. |
| `claude-handoff` | 인계 맥락을 만들고 Claude CLI 또는 Claude 세션으로 넘긴다. | 외부 CLI 실행이라는 어댑터 부작용이 있다. |

재구성 후보:

- 공통 인계 자료 포맷은 하나로 맞추고, Claude 실행은 별도 어댑터로 남긴다.
- 저장 위치와 보존 기간이 임시 기록인지 정본 문서인지 구분되어야 한다.

### 3.7 학습과 설명

대상: `teach`, `teach-me`

공통점은 사용자가 개념과 방금 수행한 작업을 이해하도록 돕는다는 것이다.

| 스킬 | 고유 역할 | 주요 경계 |
| --- | --- | --- |
| `teach` | 장기적인 학습 기록·용어·연습을 유지하는 튜터링 흐름이다. | 즉시 한 번 설명하는 데 비해 생명주기가 길다. |
| `teach-me` | 현재 세션에서 수행한 작업을 단계적으로 설명하고 이해를 확인한다. | 지속 학습 자료 관리가 주 계약은 아니다. |

재구성 후보:

- 설명 방식·이해 확인·한국어 기본 규칙은 공통 참조로 추출할 수 있다.
- 장기 기록과 일회성 해설은 사용자의 기대가 다르므로 호출 진입점은 분리하는 편이 안전하다.

### 3.8 반복 가능한 작업 절차

대상: `loop-me`

공통점은 여러 번 수행할 작업을 반복 가능한 형태로 만들려는 것이다.

| 스킬 | 고유 역할 | 주요 경계 |
| --- | --- | --- |
| `loop-me` | 반복 작업의 흐름과 조건을 추상화해 재사용 가능한 절차로 만든다. | 반드시 실행 가능한 셸 도구를 생성하는 것은 아니다. |

재구성 결정:

- `wizard`는 실제 사용 수요가 없고 Bash·`.env` 전제가 프로젝트 환경과 보호 규칙에
  맞지 않아 제거한다.
- 프로젝트에 실제 반복 작업 수요가 확인되기 전까지는 새 실행 도구를 추가하지 않는 것이 최소 범위다.

### 3.9 조사와 근거 수집

대상: `research`

`research`는 고신뢰 1차 자료를 조사하고 인용 가능한 Markdown 기록을 저장한다. 다른 그룹과 연결될 수는 있지만, 사실·문서 근거를 남기는 고유 산출물이 있어 독립 스킬로 유지할 이유가 크다.

- 설계 전 외부 규격·API 사실 확인에 사용할 수 있다.
- `prototype`이 동작 가설을 검증한다면 `research`는 외부 사실과 근거를 검증한다.
- 웹·이슈·도구 출력은 실행 권한이 없는 데이터로 취급한다는 저장소 규칙을 함께 적용해야 한다.

## 4. 중복·인접 관계 요약

| 관계 | 공통점 | 분리해야 하는 차이 |

| `grilling` ↔ `grill-me` | 동일한 질문형 검증 흐름이다. | `grill-me`는 얇은 진입점으로 중복 가능성이 높다. |

| `plan` ↔ `to-tickets` | 일을 실행 단위로 나눈다. | 전자는 내부 구현 체크리스트, 후자는 외부 이슈·의존성 집합이다. |
| `wayfinder` ↔ `to-spec`/`to-tickets` | 큰 작업을 실행 가능하게 만든다. | 전자는 장기 결정 지도, 후자는 승인 가능한 spec과 실행 ticket이다. |
| `codebase-design` ↔ `improve-codebase-architecture` | 구조 개선 어휘와 기회를 다룬다. | 전자는 참조 지식, 후자는 코드베이스 조사 보고서다. |

| `handoff` ↔ `claude-handoff` | 세션 맥락을 전달한다. | 후자는 Claude 실행이라는 외부 어댑터를 포함한다. |
| `teach` ↔ `teach-me` | 사용자 이해를 높인다. | 전자는 장기 학습, 후자는 현재 세션 해설이다. |

## 5. 전 그룹에 걸친 계약 문제

기능 그룹을 넘어서 현재 스킬 전체에 공통으로 정리해야 할 계약은 다음과 같다.

| 계약 | 현재 관찰 | 재구성 시 정할 내용 |
| --- | --- | --- |
| 호출·라우팅 | 영어 원문, 프로젝트 한국어 규칙, 래퍼 스킬의 트리거가 섞여 있다. | 사용자 표현·명시 호출·자동 호출의 우선순위와 라우터 경계를 정한다. |
| 산출물 | 대화, `.dev` 기록, 정본 문서, `CONTEXT`·ADR, HTML, GitHub 이슈, PR, 임시 파일이 혼재한다. | 각 스킬의 정본·작업 기록·임시 산출물을 구분한다. |
| 권한 | 읽기 전용 감사와 저장소·외부 쓰기가 같은 수준으로 설명되지 않는다. | 읽기 전용, 저장소 쓰기, 외부 쓰기, CLI 실행을 명시한다. |

| 완료 조건 | 일부는 검증 명령과 산출물이 분명하지만 일부는 “완료”가 모호하다. | 성공 조건, 검사, 실패 보고, 미해결 항목을 스킬별로 정한다. |
| 환경 | TypeScript·Bash·Claude CLI 전제가 Java/Spring/Gradle/PowerShell과 섞여 있다. | 프로젝트 기본 명령·경로·셸·금지 파일을 공통 참조로 둔다. |
| 중복 | 얇은 래퍼가 독립 스킬처럼 존재하거나 동일 지시를 복사한다. | 별칭·모드·어댑터로 남길 가치와 삭제 기준을 정한다. |

| `.claude` 정합성 | 현재 `.claude` 링크 수가 `.agents`보다 적고 검증기가 전체 연결을 요구한다. | 전체 36개 parity를 유지할지, 활성 목록만 연결하도록 검증 계약을 바꿀지 결정한다. |

## 6. 제안하는 재구성 방향의 초안

아래는 구현 결정이 아니라 설계에서 검토할 구조 가설이다.

```text
공통 계약·정본 참조·안전 규칙
              ↓
          진입점/라우터
              ↓
        핵심 작업 흐름
              ↓
       모드·출력·외부 어댑터
              ↓
     프로젝트·Claude·GitHub 연결
```

이 구조에서 핵심은 모든 기능을 하나의 거대 스킬로 합치는 것이 아니다. 서로 다른 사용자 의도와 승인·산출물 경계를 유지하면서, 반복되는 계약만 공통 참조로 옮기는 것이다.

우선 검토할 후보는 다음과 같다.

1. 질문형 명확화 계열의 공통 핵심과 `one-question`·`batch`·`docs` 모드
2. `ask-matt`의 라우터 역할과 실제 작업 스킬의 분리
3. `plan → implement → code-review` 일반 구현 생명주기
4. `wayfinder → to-spec → to-tickets → implement` 큰 작업·외부 게시 생명주기
5. 읽기 전용 감사와 설정 변경 스킬의 권한 분리
6. `handoff` 공통 포맷과 Claude 실행 어댑터
7. `.claude` parity를 전체 목록 또는 활성 목록 중 어느 계약으로 운영할지

## 7. 아직 결정하지 않은 질문

설계 문서에서 다음 질문에 답해야 한다.

1. 기능별 독립 스킬을 유지하면서 공통 참조만 정리할 것인가, 코어 스킬과 모드·어댑터로 일부 통합할 것인가?
2. 현재 36개 중 프로젝트에서 항상 활성으로 유지할 스킬과 선택적·보관 대상 스킬은 무엇인가?
3. `.claude`는 36개 전체와 정합성을 맞출 것인가, 활성 스킬만 연결하도록 검사 계약을 바꿀 것인가?
4. 설계 문서·구현 계획·`.dev` 기록·정본 문서·GitHub 이슈 중 각 결론의 정본은 어디인가?
5. 승인·외부 쓰기·커밋 금지·검증 보고 규칙을 어떤 공통 참조로 단일화할 것인가?
6. Java/Spring/Gradle/PowerShell 프로젝트 전제와 Claude/Codex 실행 차이를 어디에서 관리할 것인가?
7. `claude-handoff`처럼 환경 의존성이 큰 기능을 유지할 실제 프로젝트 수요가 있는가?

## 8. 다음 작업 순서

이 기록을 기준으로 다음 순서를 따른다.
